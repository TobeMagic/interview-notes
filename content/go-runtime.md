# Go 运行时

对标 JVM。GMP 和 GC 是统计里出现率最高的两题，各写一大章，不拆成十个小点。

排版约定：每题先给一句能说出口的答案，再展开，再列会被追问什么。题下紧跟已核对的公开原题。

## 调度器 GMP

### 1.🌟G、M、P 分别是什么？

**一句话**：G 是 goroutine，M 是操作系统线程，P 是处理器上下文（调度资源）。M 必须绑定 P 才能执行 G。

**展开**：

1. **G**：协程，包含栈、指令指针、状态。初始栈 2KB，按需增长。
2. **M**：内核线程，真正执行代码的实体。数量受 `GOMAXPROCS` 间接影响，但可以更多（比如阻塞的系统调用）。
3. **P**：逻辑处理器，维护一个本地 G 队列（256 个槽位）。数量等于 `GOMAXPROCS`，默认是 CPU 核数。
4. 关系：P 绑定 M 执行 G。P 的数量决定了并行度。

**追问：为什么需要 P 这一层，直接 M 调度 G 不行吗？** 因为需要一个「不占线程的调度上下文」。M 被系统调用阻塞时，P 可以解绑去绑定另一个 M，继续跑队列里的 G。没有 P 的话，本地队列和调度状态就没地方放。

**追问：`GOMAXPROCS` 设大有什么用？** 提高并行度，但超过 CPU 核数会带来线程切换开销。I/O 密集型可以略大，CPU 密集型等于核数最好。

**面经**：

### 2.🌟调度器怎么找到下一个要执行的 G？

**一句话**：先看本地队列，再看全局队列，再看网络轮询器，最后去别的 P 那里偷。

**展开**：

1. **本地队列**：P 自己的 runnext（一个高优先级槽位）+ 本地队列（256 个）。
2. **全局队列**：本地空了去全局拿，一次拿一批（`GOMAXPROCS` 或 128 个）。
3. **netpoll**：检查有没有网络 I/O 就绪的 G。
4. **work stealing**：去其他 P 的本地队列偷一半。

**追问：为什么要偷一半而不是偷一个？** 减少偷的频率。偷一个的话，每次执行完都要再偷，开销大。偷一半能保证接下来一段时间都有活干。

**追问：为什么本地队列要有 runnext？** 为了让刚创建的 G 优先执行（比如 `go f()` 之后马上执行子任务），提高局部性和响应速度。但 runnext 也会被偷。

**面经**：字节秋招一面：P 的本地队列空或者不空时怎么调度。https://www.nowcoder.com/feed/main/detail/71e75505e34f43689ce98e20f78f3ed8

### 3.🌟抢占式调度是怎么实现的？

**一句话**：Go 1.14 起用信号实现异步抢占，之前只能靠函数调用时的协作式检查点。

**展开**：

1. **协作式**（1.14 前）：编译器在函数入口插入检查，发现栈增长或 `Gosched` 时让出。死循环里没有函数调用就永远不让出。
2. **异步抢占**（1.14+）：sysmon 线程发现某个 G 运行超过 10ms，发 `SIGURG` 信号，运行时在信号处理里把 G 标记为可抢占，下次安全点让出。
3. 安全点是编译器插入的指令位置，保证栈可以安全扫描。

**追问：为什么之前死循环会卡死整个 P？** 因为协作式抢占依赖函数调用，`for {}` 没有调用，调度器没有机会介入，这个 P 就被独占了。

### 4.🌟goroutine 为什么比线程便宜？

| | 线程 | goroutine |
| --- | --- | --- |
| 初始栈 | 1–8MB | 2KB |
| 栈增长 | 固定，超了崩溃 | 按需增长，最大 1GB |
| 切换 | 内核态，保存寄存器 + TLB | 用户态，只保存少量寄存器 |
| 创建开销 | 系统调用 | 用户态分配 |
| 数量级 | 几千 | 百万级 |

**一句话**：栈小、切换在用户态、创建不经过内核，所以便宜。

**展开**：

1. 线程切换要进内核，还要刷新 TLB、处理缓存失效。
2. goroutine 切换只是保存 PC、SP 和几个寄存器，调度器在用户态完成。
3. 栈按需增长（连续栈复制），不用预留大空间。

**追问：goroutine 泄漏是什么？** 启动的 goroutine 永远阻塞，无法退出，导致内存和栈持续增长。常见原因：channel 没人收、锁永远不释放、`select` 没有 default 也没有超时。

**面经**：

- 协程调度底层约 3.83%，协程和线程的区别约 3.83%。https://www.nowcoder.com/discuss/789864350730162176
- 字节搜索后端一面：协程和线程的区别。https://www.nowcoder.com/discuss/668776138512052224

### 5.什么时候会发生 G 的阻塞和恢复？

**一句话**：系统调用、channel 操作、锁等待、`time.Sleep`、网络 I/O 都会让 G 阻塞，运行时负责把 P 让出来。

**展开**：

1. **系统调用**：M 阻塞时，P 解绑并找新 M（或创建）。系统调用返回后，G 需要重新拿一个 P 才能继续。
2. **channel / 锁**：G 进入等待队列，P 继续跑别的 G。不占用 M。
3. **网络 I/O**：G 注册到 netpoll，M 不阻塞，P 继续跑。
4. **`time.Sleep`**：G 挂到定时器上，P 让出。

**追问：系统调用和 channel 阻塞有什么区别？** 系统调用阻塞的是 M（内核态），需要额外线程；channel 阻塞只影响 G，M 和 P 都能继续工作。所以 I/O 密集用网络轮询，别用阻塞式系统调用。

**面经**：暂无已核对的公开原题。

### 6.`sysmon` 是干什么的？

**一句话**：一个独立的后台线程，不绑定 P，负责监控和清理：抢占长时间运行的 G、触发 GC、回收空闲 M、轮询网络。

**展开**：

1. 每 10ms 到 10s 不等地醒来，做不同的事。
2. 发现 G 运行超过 10ms 就发起抢占。
3. 发现 P 空闲太久就把 M 回收，减少线程数。
4. 参与 netpoll，把就绪的 G 放回队列。

**追问：`sysmon` 为什么不需要 P？** 因为它不做 Go 代码调度，只做监控和系统级操作。它可以直接操作运行时数据结构。

**面经**：暂无已核对的公开原题。

## 内存管理

### 7.🌟Go 的内存分配有哪几级？

**一句话**：mcache（每 P 私有）→ mcentral（全局，按 size class 分）→ mheap（页堆）→ 操作系统。

**展开**：

1. **mcache**：每个 P 一个，缓存各种 size class 的 span，分配时不用加锁。
2. **mcentral**：按 size class 组织，管理所有含空闲槽的 span，多个 P 共享，要加锁。
3. **mheap**：管理页（8KB 一页），向 OS 申请内存（arena）。
4. 小对象（<16KB）走 mcache，大对象直接走 mheap。

**追问：为什么要分级？** 减少锁竞争。mcache 是每 P 私有的，绝大多数小对象分配不用加锁。只有 mcache 不够时才去 mcentral 拿一批。

**追问：size class 是什么？** 把对象大小分成约 70 档（8B、16B、24B…），每档对应一种 span。这样分配时不用精确匹配，减少碎片。

**面经**：暂无已核对的公开原题。

### 8.🌟逃逸分析是什么？

**一句话**：编译器分析变量的生命周期，如果它不会逃出函数，就分配在栈上；逃出去才分配在堆上。

```go
func f() *int {
    x := 1
    return &x      // x 逃逸到堆
}

func g() {
    x := 1
    _ = x          // x 留在栈上
}
```

**展开**：

1. 栈分配不需要 GC，函数返回就回收，开销几乎为零。
2. 常见逃逸原因：返回指针、被闭包捕获、赋给接口、大小不确定（`make([]int, n)` 的 n 是变量）、发送到 channel。
3. `go build -gcflags="-m"` 能看逃逸分析结果。

**追问：逃逸分析能优化到什么程度？** 能把大量小对象留在栈上，显著减少 GC 压力。但它保守：不确定时就判逃逸。

**追问：为什么 `interface{}` 会导致逃逸？** 因为接口值要在堆上分配数据（`eface` 的 `data` 指针）。装箱操作本质就是「把值放到堆上」。

**面经**：

- 内存逃逸的排查，出现率约 3.83%，小米、深信服等。https://www.nowcoder.com/discuss/789864350730162176
- 腾讯校招一面：说说逃逸分析。https://juejin.cn/post/7434352545870184485

### 9.栈是怎么增长的？

**一句话**：goroutine 初始栈 2KB，不够时申请一块两倍大的新栈，把旧栈内容复制过去，然后释放旧栈。

**展开**：

1. 连续栈（contiguous stack）：新栈是旧栈的两倍，地址不连续。
2. 复制后要修正所有指向旧栈的指针，编译器在栈上维护指针信息。
3. 收缩：GC 时如果栈使用量小于 1/4，会缩回一半。
4. 最大栈 1GB（64 位），超过就 panic。

**追问：为什么复制栈不会导致指针失效？** 因为运行时会扫描栈上的指针并修正。这也是为什么 Go 的指针不能被随意转成整数（`uintptr` 有特殊规则）。

**面经**：暂无已核对的公开原题。

## 垃圾回收

### 10.🌟Go 的 GC 是三色标记，具体怎么做的？

**一句话**：白（未访问）、灰（已访问但子对象未扫完）、黑（已访问且子对象扫完）。从根对象开始把可达对象染黑，剩下的白色就是垃圾。

**展开**：

1. **标记准备**：STW，开启写屏障，初始化扫描任务。
2. **并发标记**：从根（栈、全局变量、寄存器）开始，把对象染灰，然后逐个处理灰色对象，把它引用的对象染灰，自己染黑。
3. **标记终止**：STW，关闭写屏障，完成剩余标记。
4. **并发清除**：回收白色对象的内存。

**追问：为什么需要三色，两色不够吗？** 两色（黑/白）在并发标记时无法区分「已扫描」和「未扫描」，会漏标或重复扫描。灰色是「待处理」的中间状态。

**追问：STW 有多长？** 现代 Go 的 STW 在微秒到毫秒级，主要是标记准备和终止两个短暂停顿。大部分标记工作是并发做的。

**面经**：

- 三色标记和写屏障，出现率约 8.99%，百度、字节、腾讯音乐等。另一题「简述 GC」约 6.66%，字节、滴滴等。https://www.nowcoder.com/discuss/789864350730162176
- 腾讯校招一面：GC 扫描是不是并发的；根对象有哪些。https://juejin.cn/post/7434352545870184485

### 11.🌟写屏障解决什么问题？

**一句话**：并发标记时用户程序还在改指针，写屏障保证「不漏标」——新创建或被修改的引用不会被当成白色回收。

**展开**：

1. **漏标条件**：一个白色对象被黑色对象引用，同时这个白色对象原来的灰色引用被删除。此时黑色不会重新扫描，白色被误回收。
2. **强三色不变式**：不允许黑色指向白色。插入屏障在写入时把白色染灰。
3. **弱三色不变式**：允许黑色指向白色，但白色必须通过灰色可达。删除屏障在删除时把被删的引用染灰。
4. **混合写屏障**（Go 1.8+）：结合两者，被覆盖的对象染灰，新写入的对象也染灰。这样栈不需要重新扫描。

**追问：为什么混合写屏障能让栈不用重新扫描？** 因为栈上的对象在标记开始时被整体染黑（而不是逐个扫描），之后栈上新建的对象由写屏障染灰。这样避免了 STW 期间重新扫描所有栈。

**面经**：三色标记和写屏障约 8.99%。https://www.nowcoder.com/discuss/789864350730162176

### 12.🌟`GOGC` 和 `GOMEMLIMIT` 分别调什么？

**一句话**：`GOGC` 控制「堆增长多少百分比触发 GC」，`GOMEMLIMIT` 控制「内存上限」，后者是软限制。

**展开**：

1. `GOGC=100`（默认）：堆增长到上次 GC 后的 2 倍就触发。
2. `GOGC=off`：关闭 GC（调试用，会 OOM）。
3. `GOMEMLIMIT`（1.19+）：设置软上限，接近时更激进地 GC。超过不会立刻 OOM，但会持续 GC 直到降下来。
4. 两者配合：`GOMEMLIMIT` 设成容器内存的 80–90%，`GOGC` 让它在限额内自适应。

**追问：为什么推荐设 `GOMEMLIMIT`？** 因为容器有内存上限，`GOGC` 只看相对增长，内存基数大时可能涨到超过容器限额被 OOMKill。`GOMEMLIMIT` 让 GC 感知绝对上限。

### 13.GC 的触发时机有哪些？

**一句话**：堆增长达到 `GOGC` 阈值、定时触发（2 分钟没 GC）、手动 `runtime.GC()`、内存接近 `GOMEMLIMIT`。

**展开**：

1. 主要靠堆增长触发。
2. 强制 GC 会 STW，生产环境慎用。
3. `debug.SetGCPercent()` 运行时动态调。
4. GC 频率高会导致 CPU 占用高，频率低会导致内存占用高，要找平衡。

**追问：GC 频繁是什么原因？** 可能是分配速率太高（大量临时对象）、`GOGC` 设得太小、或者内存泄漏导致每次回收都回收不掉。先看 `GODEBUG=gctrace=1` 的输出。

## 性能排查

### 14.🌟pprof 怎么用？

**一句话**：采集 CPU、内存、goroutine、锁、阻塞等 profile，用 `go tool pprof` 分析火焰图。

```go
import _ "net/http/pprof"
go http.ListenAndServe(":6060", nil)
```

**展开**：

1. `go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30` 采 CPU。
2. `go tool pprof http://localhost:6060/debug/pprof/heap` 采堆。
3. 进入交互后 `top`、`list 函数名`、`web`（生成火焰图）。
4. 生产环境暴露 pprof 要用独立端口 + 鉴权，别开在业务端口。

**追问：CPU profile 和 heap profile 分别看什么？** CPU 看「哪里在烧 CPU」，是采样（默认 100Hz）。heap 是「当前堆上有什么」，看 `inuse_space`（占用）和 `alloc_space`（累计分配）。

**追问：`alloc_objects` 和 `inuse_objects` 有什么区别？** `alloc_*` 是累计分配量，用来找「分配最频繁的地方」；`inuse_*` 是当前存活量，用来找「内存被谁占着」。

### 15.🌟goroutine 泄漏怎么排查？

**一句话**：看 goroutine 数量是否持续增长，用 pprof 的 goroutine profile 看它们卡在哪个调用栈。

**展开**：

1. `runtime.NumGoroutine()` 打点监控，持续增长就是泄漏。
2. `go tool pprof http://localhost:6060/debug/pprof/goroutine` 看调用栈分布。
3. 常见原因：channel 没人接收、`select` 没超时、锁没释放、HTTP 请求没设超时。
4. 加 `debug=1` 参数能看到每个 goroutine 的完整栈。

**追问：怎么预防？** 每个 goroutine 都要有明确的退出路径：`context` 取消、channel 关闭、超时。代码审查时看「这个 `go func()` 什么时候退出」。

### 16.`GODEBUG=gctrace=1` 输出怎么看？

**一句话**：每次 GC 打一行，包含 GC 序号、堆大小、STW 时长、标记和清扫耗时、并发度。

```
gc 12 @3.456s 2%: 0.012+1.2+0.003 ms clock, ...
```

**展开**：

1. `gc 12` 是第 12 次 GC，`@3.456s` 是启动后时间。
2. `2%` 是 GC 占用的 CPU 比例，太高说明 GC 太频繁。
3. `0.012+1.2+0.003` 分别是 STW（标记准备）、并发标记、STW（标记终止）的耗时。
4. 堆大小从多少降到多少，能看出回收效果。

**追问：什么指标算异常？** GC 占比超过 5%、STW 超过 1ms、GC 间隔越来越短（说明分配速率高或泄漏）。要结合业务 QPS 看。

### 17.什么是「假共享」？

**一句话**：两个 CPU 核改同一个缓存行里的不同变量，导致缓存行反复失效，性能急剧下降。

```go
// 两个字段在同一缓存行，两个 goroutine 各改一个
type Counter struct {
    a int64
    b int64   // 和 a 在同一 64 字节缓存行
}
```

**展开**：

1. CPU 缓存以 64 字节的缓存行为单位，一个核改了缓存行里的任何字节，其他核的副本都失效。
2. Go 的 `sync/atomic` 类型有 `pad` 字段，就是用来填充避免假共享。
3. 解法：加填充（`_ [56]byte`）或者把热字段分开。

**追问：Go 标准库哪里用了这个技巧？** `sync.Pool` 的 per-P 结构、`atomic.Int64` 内部的 `align64` 填充。自己写并发计数器时也有用。

**面经**：暂无已核对的公开原题。
