# Go 语言

对标 Java SE 与集合里属于语言本身的部分。GMP、GC 在运行时篇，channel 和锁在并发篇。

每一节按大脑记忆四步法编排：**记忆锚点**（一秒抓骨架）→ **痛点与直觉**（为什么这么设计 + 物理类比）→ **核心机制**（空间图解 + 3 个核心组块）→ **考场口述**（30 秒第一人称串词）。

## 语言与编译

### 1.🌟Go 是一门什么样的语言

**记忆锚点**：**自带干粮的静态二进制**——编译期变成机器码，运行时编进文件里，没有外部虚拟机。

**痛点与直觉**：

2009 年 Google 内部大量服务是高并发、I/O 密集、逻辑不复杂。C++ 编译慢、依赖乱；Java 要装 JVM、启动要预热、内存基线高。Go 的取舍全指向四件事：编译快、一个文件就能部署、并发写进语言里、GC 停顿守在毫秒级而不是追求极致吞吐。把它想成**自带厨房的盒饭**：吃的时候不用再找一口锅（JVM），锅已经焊在盒子里。

**核心机制**：

```
.go 源码 → 解析 AST → 按包类型检查 → 编译成 .o → 链接成单个可执行文件
                                              └── 运行时一并打进二进制
运行时负责：goroutine 调度、GC、map 哈希随机化、channel、栈增长
崩溃栈里的 runtime.gopark、runtime.mallocgc 就是它，不是外部进程
```

1. **有运行时，没有虚拟机**：运行时是链进去的库，进程起来就是机器码。启动没有类加载、没有 JIT 预热，所以是毫秒级；代价是少了「越跑越快」的 JIT，长跑性能更依赖代码本身。
2. **和 Java 的三处对照**：产物是单个二进制而不是 `.class`；泛型从 1.18 起、编译期实例化，不是 Java 1.5 那种擦除；并发是 goroutine，不是线程池。
3. **交叉编译是默认能力**：`GOOS=linux GOARCH=amd64 go build` 可以在 Mac 上打出 Linux 二进制。不依赖目标机的 C 库时，镜像可以 `FROM scratch`。

**考场口述**：

「Go 是静态编译型语言，产物是一个可以直接执行的原生二进制，运行时被链接进这个文件，不是外面再挂一个虚拟机。我用三点和 Java 对照：第一，没有类加载和 JIT 预热，启动是毫秒级，但长跑也不会越跑越快；第二，部署就是拷一个文件，交叉编译靠 `GOOS` 和 `GOARCH`；第三，并发和 GC 都在语言自带的运行时里，崩溃栈上的 `runtime.gopark`、`runtime.mallocgc` 就是证据。泛型是 1.18 才有的，实现方式是编译期实例化，不是 Java 的类型擦除。」

### 2.包的初始化和 `init`

**记忆锚点**：**先把被依赖的包叫醒，再算本包变量，最后跑 `init`，然后才是 `main`**。

**痛点与直觉**：

Go 没有构造函数，也没有应用级启动钩子。包只要被 import，就会自己跑起来。这像**进门就自动通电的电器**：驱动、编解码器靠这个注册很方便，但你很难一眼看出插上电源时到底启动了哪些电器。

**核心机制**：

```
被 import 的包（递归，先初始化依赖）
    └─ 该包的包级变量（被引用的先算）
         └─ 该包的 init
本包的包级变量 → 本包的 init → main
同包多个 init：文件名字典序，文件内按出现顺序
```

1. **下划线导入只要副作用**：`import _ "github.com/lib/pq"` 不使用任何导出符号，但会跑对方的 `init`，里面 `sql.Register("postgres", ...)`。所以只 import 不调用，`sql.Open("postgres", ...)` 也能用。
2. **`init` 不能失败得体面**：没有返回值，出错只能 `panic` 或 `log.Fatal`。测试一个包就会跑它的 `init`，可能连上外部数据库。
3. **新代码把启动交给调用方**：显式 `New()` 或 `Register()`。标准库里 `init` 还很多，但隐式副作用让启动链路难追，也会把用不到的包一起初始化。

**考场口述**：

「导入一个包时，先递归初始化它依赖的包：每个包先按依赖算包级变量，再执行 `init`，全部完成后才到本包，最后进 `main`。同一个包里多个 `init` 按源文件名字典序、文件内从上到下。空白导入就是为了要这个副作用，数据库驱动靠它注册。我会补三个限制：`init` 不能返回错误，测试会把它一起跑掉，而且所有被导入的包都会初始化。所以新代码我更倾向显式 `New` 或 `Register`。」

### 3.包和模块

**记忆锚点**：**仓库装模块，模块装包；`go.mod` 锁版本，`internal` 锁可见性**。

**痛点与直觉**：

1.11 之前所有代码必须放在 `GOPATH` 下，`go get` 拉的是当时的最新版，线上和本地经常不是同一份代码。模块把「这堆包是哪个版本」写进文件，像给工具箱贴了**零件清单和防拆封条**（`go.sum` 的哈希）。

**核心机制**：

```
仓库 git repo
  └─ 模块  go.mod 里的 module 路径     go 1.22  这行同时是语言版本门
       └─ 包  一个目录，目录内同属一个 package
require 声明依赖；replace 只替换当前模块；go.sum 记内容哈希，必须入库
```

1. **三层不要混**：仓库是 git 边界，模块是版本边界，包是编译边界。一个目录只能有一个包。`go` 那一行不只是工具版本，它决定循环变量这类语言语义（见第 30 节）。
2. **最小版本选择，不是尽量用最新**：每个依赖只保留能满足所有 `require` 的最低版本，构建可复现，和 npm 的浮动最新相反。`go mod tidy` 补上用到但没写的、删掉写了但没用的，并更新 `go.sum`。
3. **可见性只有 `internal`**：`internal` 下的包只能被它的父目录树导入，语言里没有 `private package`。另外，`v2` 及以上的模块路径必须带 `/v2`，否则会被当成另一个模块；`replace` 不传递给依赖你的人；私有仓库要设 `GOPRIVATE`，否则会去走公共代理。

**考场口述**：

「模块是 `go.mod` 描述的版本单元，包是一个目录里的编译单元。`go` 指令同时声明语言版本，循环变量的新语义就由它门控。依赖选择用最小版本选择，每个依赖只留满足全部要求的最低版本，`go.sum` 记的是内容哈希，必须提交。可见性上，Go 没有私有包，只靠 `internal` 目录限制谁能导入。大版本从 v2 起路径要带 `/v2`，`replace` 只对当前模块有效。」

## 基础类型

### 4.🌟Go 有哪些基本类型

**记忆锚点**：**没有装箱、没有隐式转换；`byte` 是字节，`rune` 是码点，`int` 的宽度跟着平台走**。

**痛点与直觉**：

C 里 `int` 和 `long` 混算，溢出发生在你没看见的那一次提升里。Go 把这件事说死：两个类型要运算，必须你亲手写出转换。啰嗦是故意的，换来的是**不用猜这里会不会自动转**。

**核心机制**：

```
bool
int8 int16 int32 int64     int     32 位平台 32 位，64 位平台 64 位
uint8 uint16 uint32 uint64 uint uintptr
float32 float64            没有 float
string
byte = uint8               一个字节
rune = int32               一个 Unicode 码点

"你好"  len = 6 字节；utf8.RuneCountInString = 2；range 给出的是码点
```

1. **数值零值是 0，布尔是 false，字符串是空串，指针和容器是 nil**：转换必须显式，`int` 和 `int64` 不能直接相加。
2. **协议和序列化用固定宽度**：`int` 的位数随平台变，写进文件或跨机器的字段用 `int32` / `int64`。`uintptr` 只是能装下指针的整数，GC 不追踪它，只能在 `unsafe` 里短暂使用。
3. **`byte` 走编码，`rune` 走字符**：下标取的是字节，`range` 得到的是码点。中文一个字常常是 3 个字节，用 `len` 当字数一定会错。

**考场口述**：

「Go 的基本类型就是布尔、按位宽分开的整数、float32 和 float64、复数、字符串。没有隐式转换，`int` 和 `int64` 不能直接运算。两个别名要分开说：`byte` 是 `uint8`，处理字节；`rune` 是 `int32`，处理 Unicode 码点。所以 `len("你好")` 是 6，不是 2。另外 `int` 的宽度跟平台走，序列化必须用固定位宽；`uintptr` 是整数不是指针，GC 不会顺着它找对象。」

**面经**：

### 5.🌟Go 只有值传递，怎么理解

**记忆锚点**：**传参永远复印一份；slice、map、channel 复印的是带指针的头部，不是底层数据**。

**痛点与直觉**：

函数里改了 slice 元素，外面看得到，于是有人说 Go 是引用传递。参照物要换一下：电影票存根上写着排和座号，复印存根不会搬走座椅，但拿着任何一张存根都能去改那张座椅上的名字。重新发一张存根（给参数重新赋值）不影响观众手里那张。

**核心机制**：

```
实参 ──复印──► 形参
int / struct     复印整份值          形参重新赋值，外面不变
*T               复印地址            解引用改的是同一块
slice            复印 {ptr,len,cap}  改元素外面看得到；append 换了新数组则外面看不到
map / chan       复印内部指针        改内容外面看得到；形参 = nil 外面不变
```

1. **判断标准是「重新赋值影不影响外面」**：`func setNil(m map[string]int) { m = nil }` 不会把调用方的 map 变成 nil。引用传递才会。所以 Go 只有值传递。
2. **slice 最隐蔽**：没扩容的 `append` 写进共享底层数组，但调用方的 `len` 不变，新元素用下标看不见，内存里已经脏了。扩容之后形参指向新数组，调用方仍指向旧的。
3. **结构体传指针的三个理由，占一条就该用指针**：要修改、拷贝太贵、这个类型已经有指针接收者。最后一条是为了方法集一致，否则接口实现会对不上。

**考场口述**：

「Go 只有值传递，没有引用传递。判断标准是：函数里给参数重新赋值，永远不影响外面。slice、map、channel 看起来像引用，是因为它们的值里面本来就有指针，复印的是这个头。所以改 slice 元素、往 map 里写，外面看得到；但在函数里 `m = nil` 或扩容后的新 slice 头，外面看不到。结构体默认传值，要修改、体量大、或者已经在用指针接收者，这三条占一条我就传指针。」

**面经**：

- 腾讯 · 校招一面：Go 中的参数传递是值传递还是引用传递。https://segmentfault.com/a/1190000045455181

### 6.🌟零值是什么，为什么它很重要

**记忆锚点**：**声明出来就能用的那些，是零值可用；能读不能写的，是 nil map**。

**痛点与直觉**：

Java 里很多对象在 `new` 之前是 null，一碰就炸。Go 反过来，希望 `var x T` 就已经是一个能工作的值，这样标准库可以少要构造函数：`var buf bytes.Buffer`、`var mu sync.Mutex` 拿来就用。零值可用不是「零值什么都能做」，而是**设计类型时让零值处在安全的那一侧**。

**核心机制**：

```
数值 0    布尔 false    字符串 ""
指针 / 接口 / 函数 / slice / map / chan   nil

nil slice    len 0，可以 append、可以 range
nil map      可以读到零值，写入 panic
nil chan     读写都永久阻塞
nil func     调用 panic
nil slice 序列化成 null；空 slice（非 nil）序列化成 []
```

1. **四条边界**：slice 能追加，map 只能读，channel 会堵死，函数一调就崩。新手最常见的 panic 是往 nil map 里赋值。
2. **空和 nil 不是同一个值**：`var a []int` 是 nil；`[]int{}` 和 `make([]int, 0)` 长度也是 0，但不是 nil。接口如果把数组返回给前端，`null` 和 `[]` 是两种 JSON。
3. **接口的 nil 还有第二层**：装了一个 nil 具体指针的接口，自身不等于 nil。这个坑放在第 21 节，这里先记住「类型指针和数据指针要同时为空」。

**考场口述**：

「Go 的每个类型都有零值，`var x T` 不用构造就能读。`bytes.Buffer`、`sync.Mutex` 的零值就能用，这是故意少写构造函数。但零值可用有边界：nil slice 可以 append，nil map 读取返回零值、写入直接 panic，nil channel 读写永久阻塞，nil 函数一调用就 panic。另外 nil slice 和空 slice 长度都是 0，JSON 却分别是 `null` 和 `[]`。接口还有一个更隐蔽的 nil，类型信息非空时，接口本身不是 nil。」

### 7.常量与 `iota`

**记忆锚点**：**`const` 块里 `iota` 从 0 起，每行加 1；它不是枚举，`Weekday(99)` 照样能过编译**。

**痛点与直觉**：

Go 没有 `enum` 关键字。一组有限取值如果手写 0、1、2，中间插一行就会全部错位。`iota` 是编译器替你数行号：像**稿纸左侧的行号**，换一行自动加一，你只需要决定第一行的公式。

**核心机制**：

```go
type Weekday int
const (
    Sunday Weekday = iota // 0
    Monday                // 1  省略的类型和表达式，沿用上一行
    Tuesday               // 2
)
const (
    _ = iota
    KB = 1 << (10 * iota) // 1 << 10
    MB                    // 1 << 20
)
```

1. **计数器属于这个 const 块**：每遇到一行常量声明加 1，新的 `const (` 从 0 再来。位标志写成 `1 << iota`。用 `_` 吃掉 0。
2. **无类型常量在编译器里是高精度**：`const big = 1 << 100` 可以先写着，赋给 `int64` 时才检查放不放得下，溢出在赋值那一刻报错。
3. **它约束不了取值范围**：底层是整数的自定义类型，随便一个数字都能转进去。要限制就自己写 `Valid()`。常量也不能是 slice、map、struct，因为值必须编译期就定下来。

**考场口述**：

「Go 没有枚举关键字，惯用法是自定义整数类型加 `const` 块，用 `iota` 从 0 开始每行加 1。省略的行会复用上一行的类型和表达式，所以位标志可以写成 `1 << iota`。它和真枚举的差别是：编译器不检查取值，`Weekday(99)` 合法，范围要自己校验。另外无类型常量在编译器内部是高精度的，直到赋给一个具体类型才做溢出检查。」

### 8.类型转换、断言、类型开关

**记忆锚点**：**`T(v)` 是换一种类型看；`v.(T)` 是把接口拆开，失败会 panic，除非接住 ok**。

**痛点与直觉**：

两套语法都像「变成别的类型」，干的事完全不同。转换是同一块数据换个尺子量，尺子必须本来就兼容。断言是打开一个贴了封条的盒子，封条上写的具体类型如果不是你要的，单返回值形式会直接 panic。外部输入不该用会炸的那一种。

**核心机制**：

```go
f := float64(i)             // 转换：类型必须兼容
s, ok := x.(string)         // 断言：只用于接口；ok 为 false 时不 panic
switch v := x.(type) {      // 每个 case 里 v 已经是那个具体类型
case string:
case int:
}
var x any = &T{}
_, ok := x.(T)              // false，盒子里装的是 *T
```

1. **转换不看接口里装了什么**：它用于数值之间、`string` 和 `[]byte` 之间。截断和精度损失由你负责，编译器只检查类型是否允许这样转。
2. **断言只拆一层**：它回答「这个接口的动态类型是不是 T」。值和方法指针是两种类型，`T` 和 `*T` 对不上就是失败。要看结构体字段、按名字调方法，才轮到 `reflect`。
3. **类型开关是批量断言**：`v` 在每个 case 里被收窄成那个分支的类型，`default` 里仍是原接口。外部数据一律用双返回值的断言。

**考场口述**：

「类型转换 `T(v)` 要求两种类型兼容，比如 int 转 float64、string 转字节切片。类型断言 `v.(T)` 只能用在接口上，是把里面的具体类型取出来。单返回值失败会 panic，所以外部输入必须写成 `s, ok := v.(string)`。类型开关是它的多分支形式，每个 case 里变量已经是具体类型。另外值和指针算不同类型，盒子里装的是 `*T` 时，断言成 `T` 会失败。」

**面经**：

### 9.结构体、嵌入与组合

**记忆锚点**：**嵌入是「把别人的字段和方法抬上来」，不是「我变成了它」；方法的接收者仍是内层**。

**痛点与直觉**：

继承会让子类同时背负「是一个父类」和「能看见父类的内部」。Go 只有组合：把 `Base` 不写字段名地放进 `User`，外面可以写 `u.ID`、`u.Describe()`，看起来像继承。但 `Describe` 的接收者仍是 `Base`，它看不见 `User.Name`。这是**名片夹进了工牌套**，别人能透过套子看见名片，套子本身并没有变成那张名片。

**核心机制**：

```go
type User struct {
    Base          // 匿名字段：字段和方法提升到 User
    Name string
}
u.Describe()      // 等价 u.Base.Describe()，接收者是 Base
```

1. **三条例外说明它不是继承**：`User` 和 `Base` 类型独立，不能把 `User` 当成 `Base` 用；提升方法改不到外层字段；外层可以声明同名方法遮蔽内层，但内层方法里的调用仍走内层，没有多态分派。
2. **嵌入接口等于委托**：结构体嵌入 `io.Reader` 就自动有 `Read`，调用转到里面那个值。这是装饰和测试替身的常用写法，要防里面是 nil。
3. **比较和冲突**：所有字段都可比较时，结构体才能 `==`；里面有 slice、map、func 就不能比。两个嵌入类型撞了同名字段，外层直接用这个名字会编译失败，必须写成 `u.A.X`。嵌值是一份拷贝，嵌指针才共享，也要处理 nil。

**考场口述**：

「Go 没有继承，用嵌入做组合。匿名字段的字段和方法会提升到外层，所以能写 `u.ID` 和 `u.Describe()`。它不是继承，有三个证据：外层和内层类型不兼容；提升方法的接收者仍是内层，看不到外层字段；外层同名方法只是遮蔽，不会改变内层对自己的调用。两个结构体能不能 `==`，取决于字段是不是都能比较，含 slice、map、函数的结构体不能直接比。」

## slice 与数组

### 10.🌟`make` 和 `new` 有什么区别

**记忆锚点**：**`new(T)` 给你一个指向零值的指针；`make` 只伺候 slice、map、channel，返回已经能用的值**。

**痛点与直觉**：

`new` 只做一件事：分配一块 T 的零值，把地址交给你。slice、map、channel 的零值是 nil，光有地址不够，它们内部还要有数组、哈希表或队列。`make` 就是专门把这三样的内部结构装好的扳手，别的类型它不接。

**核心机制**：

```
new(int)              *int，指向 0
new([]int)            *[]int，指向 nil slice，几乎没用
make([]int, len, cap) 返回 slice 头，底层数组已分配
make(map[K]V)         返回可写的 map
make(chan int, n)     返回带缓冲的 channel
```

1. **返回的东西不一样**：`new` 永远返回指针；`make` 返回的是 slice、map、channel 这三个值本身，不是它们的指针。
2. **slice 的三个参数**：`make([]T, 3)` 是 len=cap=3，元素已是零值；`make([]T, 0, n)` 长度是 0、容量是 n，用来预分配，后面 `append` 在容量内不再搬家。
3. **nil map 必须先 `make` 或写成字面量才能赋值**：`var m map[string]int; m["a"] = 1` 会 panic。业务里要指针时，`&T{}` 比 `new(T)` 更常见。

**考场口述**：

「`new(T)` 分配 T 的零值并返回 `*T`，对所有类型都适用。`make` 只用于 slice、map、channel，因为这三者的零值是 nil，必须先建好内部的数组、哈希表或队列，返回的是值本身不是指针。slice 最常用 `make([]T, 0, n)` 把容量一次留够。`new([]int)` 能编译，但拿到的是指向 nil slice 的指针，实际不会这么写。」

### 11.🌟slice 的底层结构

**记忆锚点**：**slice 是一张三格存根：指针、长度、容量；复印存根不复印整个放映厅**。

**痛点与直觉**：

slice 不是「会自己变长的数组」这一个东西。变量里只有三个字：底层数组从哪一格开始、现在能看见几格、从起点最多能用到几格。函数调用复印的是这张存根。两张存根指向同一排座位时，改某一格两边都看得到；其中一张去换了一座新厅（扩容），另一张还坐在老厅。

**核心机制**：

```
slice 头                 底层数组
┌──────────────┐        ┌───┬───┬───┬───┬───┐
│ ptr ─────────┼───────►│ 1 │ 2 │ 3 │   │   │
│ len = 3      │        └───┴───┴───┴───┴───┘
│ cap = 5      │
└──────────────┘
传参只复印这 3 个字
```

1. **改元素外面看得到，换头外面看不到**：下标赋值写的是共享数组。`append` 如果触发扩容，函数内的头指向新数组，调用方的头原封不动，所以 `append` 的结果必须接住。
2. **没扩容的 append 更阴**：容量够时，元素写进调用方 `len` 之外、`cap` 之内的那一格。调用方 `len` 仍是旧的，打印 slice 看不到，但 `s[:cap]` 或另一张更长的存根能看见脏数据。
3. **大切片会把大数组留在内存里**：`return big[:10]` 这张新头仍然指着整块 `big`。要断开就 `copy` 到一块刚好 10 字节的新数组。`s = s[:0]` 只把 len 清零，底层数组和里面的指针都还在，GC 不会收。

**考场口述**：

「slice 是一个结构体值，里面是指向底层数组的指针、len 和 cap。传参拷贝的是这三个字，所以函数里改元素，外面看得到。`append` 必须接收返回值：容量不够时它会换一块新数组，函数里的新头不会自动写回调用方；容量够时它会写进共享数组里 len 之外的位置，外面长度不变但内存已经被改了。还有一个泄漏：小切片如果是从大数组上切出来的，整块大数组都回收不了，需要 copy 一份断开。」

### 12.🌟slice 的扩容机制

**记忆锚点**：**256 以下翻倍，256 及以上按大约 1.25 倍一步步加，最后再对齐到 size class**。

**痛点与直觉**：

小切片如果每次只加一格，拷贝次数会爆炸；一直翻倍，大切片一次就要申请近一倍的空位，内存碎片和 GC 压力都上来。所以增长先猛后缓：小孩的衣服买大一号，大人的衣服只放一截。真正分到的容量还要迁就内存分配器的格子，不会刚好等于你算出来的数。

**核心机制**：

```
需要的长度 = 旧 len + 新增元素数
若旧 cap < 256：新 cap 先按 2 倍
若旧 cap ≥ 256：反复加上 (cap + 3×256) / 4，直到够用
                 这一步大约是 1.25 倍，不是「新容量等于这个公式」
然后再向上对齐到分配器的 size class，所以 cap 可能是 48、96 而不是整数倍
```

1. **公式是增长量，不是新容量本身**：`(oldcap + 3*256) / 4` 是每次往上加的那一截。旧容量很大时，新容量约是原来的 1.25 倍。面试里说「大约 1.25 倍，并且会按 size class 对齐」，不要说「一定翻倍」。
2. **预分配省掉中间那几次搬家**：`make([]T, 0, n)` 之后在容量内 append，只写元素不分配。已知长度往已有切片填数据时，`copy` 比 `append` 少一次容量检查。
3. **旧数组不一定立刻消失**：还有别的 slice 指着它，它就活着。扩容只保证返回的那张新头指向新数组。

**考场口述**：

「`append` 容量不够时会分配新数组、拷贝旧元素、返回新的 slice 头。增长规则从 Go 1.18 起分界：旧容量小于 256 时翻倍；大于等于 256 时，每次增加大约 `(cap + 3*256) / 4`，也就是 1.25 倍左右，避免大切片一次翻倍造成浪费。算完还会向上对齐到内存分配器的 size class，所以 cap 不一定是整数倍。因此我会说大约翻倍或大约 1.25 倍，不说一定是某个数。元素个数已知时，用 `make` 把 cap 一次留出来。」

### 13.数组和 slice 的区别

**记忆锚点**：**数组的长度写进类型；slice 的长度写在运行时的头里**。

**痛点与直觉**：

`[3]int` 和 `[4]int` 是两种类型，像两只尺寸不同、不能互换的箱子，赋值时把箱子里的东西全部抄一遍。slice 是贴在箱子上的窗口，窗口可以滑动，抄窗口不抄箱子。所以数组能当 map 的 key，slice 不能——map 要求 key 能比较，窗口本身没有「两个窗口是否相等」的定义，只能和 nil 比。

**核心机制**：

```
[3]int    长度是类型的一部分    赋值整块拷贝    可以 ==
[]int     长度在 slice 头里    赋值只拷贝头    只能和 nil 比较
[1000]int 当参数              每次调用抄 1000 个元素，应改传指针或 slice
```

1. **数组适合当固定缓冲和 map key**：`[32]byte` 做哈希摘要、和 C 交互的定长缓冲。元素可比较时，数组可比较，因此能做 key；slice 不行。
2. **函数签名不要绑死长度**：`func f(a [1000]int)` 每次拷贝整块。要么 `*[1000]int`，要么 `[]int`。
3. **slice 的底层就是数组**：`make([]int, 3)` 背后有一块长度为 3 的数组，只是这块数组没有自己的类型名字暴露给你。

**考场口述**：

「数组是定长值类型，长度是类型的一部分，`[3]int` 和 `[4]int` 不能互相赋值，赋值和传参都是整块拷贝，元素可比较时数组也可以 `==`，所以能当 map 的 key。slice 是带头的值，传参只拷贝指针、长度和容量，底层数组共享，slice 之间不能 `==`，只能和 nil 比。业务里很少直接传大数组，固定大小的缓冲区和摘要才会用数组。」

## map

### 14.🌟map 的底层结构（Go 1.24 之后）

**记忆锚点**：**1.24 辞旧桶迎 Swiss：外层目录切小表，内层 8 槽配 1 个控制字，一次比对 8 个指纹**。

**痛点与直觉**：

2010 到 2024 年的 map 像一排抽屉：每个桶放 8 对键值，装不下就挂溢出桶，查找要顺着链走，扩容时新旧两套桶并存。Go 1.24 换成 Swiss Table。每 8 个槽上方有一块 64 位门牌，找人时先拿哈希低 7 位和门牌同时比对，多数槽一眼就被排除，不用把键逐个请出来。

**核心机制**：

```
map
 ├─ table 0     每张表最多约 1024 条，哈希高位选表
 ├─ table 1
 └─ ...
表内一组：
控制字 64 位 = 8 个字节，每字节：状态 + 7 位 h2
槽：key key key key key key key key
查找：高位定表 → h2 与控制字并行比对 → 候选槽再做完整键比较 → 未命中按探测序列下一组
删除满组里的槽：标墓碑，不能标成空，否则探测提前停止
扩容：以表为单位拆，单次上限是搬一张约 1024 条的表
```

1. **先说版本，再讲当前结构**：1.24 之前是 `hmap` + `bmap`，每桶 8 个键，溢出桶拉链，渐进式双桶搬迁。1.24 起是可扩展哈希目录加 Swiss Table。答只背旧桶，等于答错了当前实现。
2. **快在控制字**：64 位哈希拆出低 7 位 `h2`。一次位运算就能筛掉一组里的大多数槽，完整键比较只发生在指纹命中的候选上。
3. **墓碑、随机遍历、按表扩容**：开放寻址碰到「空」就停止，所以删除只能打已删标记，扩容重排时再清掉。遍历顺序每次随机起点，禁止依赖顺序。哪张表满了扩哪张，而不是整张 map 一起搬。

**考场口述**：

「Go 的 map 在 1.24 完全重写了。之前是每桶 8 个键加溢出桶的拉链，扩容靠渐进式搬迁；1.24 起是 Swiss Table。我讲三点：第一，顶层按哈希高位把数据分到多张表，每张大约不超过 1024 条，满了就单独拆这张表；第二，表内 8 个槽配一个 64 位控制字，每字节放状态和 7 位哈希指纹 h2，查找时一次并行比对整组，再对候选做完整键比较；第三，删除不能把槽标成空，否则探测链会断，所以留墓碑。遍历顺序是故意随机的，不能依赖。」

### 15.🌟map 为什么并发不安全

**记忆锚点**：**并发读写不是 panic，是 `throw` 出来的 fatal，`recover` 接不住**。

**痛点与直觉**：

map 内部会搬家、会改控制字。两个 goroutine 一个在写、一个在读，读到一半的结构，结果不是「偶尔读到旧值」，而是内存已经损坏。运行时发现这个窗口后选择直接让进程退出：脏着继续跑，比崩溃更危险。检测不是每次都做全量校验，所以「跑了一周没炸」不能证明安全。

**核心机制**：

```
写 map 时置标志，读 map 时抽查
撞上「别人正在写」→ runtime.throw
fatal error: concurrent map read and map write
不走 panic，不跑你的 recover，进程退出

修法：
写多、要遍历     sync.RWMutex + 普通 map
读多、键稳定     sync.Map
极高并发         按 key 哈希分片，每片一把锁
```

1. **fatal 和 panic 的分界**：`panic` 还能在本 goroutine 的 `defer` 里 `recover`。并发 map 走的是 `throw`，和栈溢出、OOM 一类，进程级退出。
2. **检测是抽样**：不是每次读写都做完整检查。数据竞争可能存在很久才撞上那个标志位。
3. **三种修法按访问形态选**：锁保护的普通 map 最直白，遍历也确定；`sync.Map` 不是通用替代；分片锁把竞争降到单片，实现和扩容都更重。只并发读、没有写，内置 map 可以同时读。

**考场口述**：

「内置 map 不是并发安全的。运行时在写的时候打标志，读的时候抽查，发现并发读写就 `throw`，报 `fatal error: concurrent map read and map write`。这不是 panic，`recover` 抓不住，进程直接退出，而且检查是抽样的，没崩不代表没竞争。修法按场景：写多或者要遍历，用 `RWMutex` 包普通 map；读多且键集合稳定，用 `sync.Map`；并发特别高再考虑按 key 分片加锁。」

### 16.🌟`sync.Map` 和 `RWMutex` 怎么选

**记忆锚点**：**读走原子快路径，新键进 dirty 互斥兜底，miss 多了再把 dirty 晋升成新的 read**。

**痛点与直觉**：

缓存的典型形态是：键写进去之后很少再变，大量 goroutine 只读。如果每次读都拿读写锁，锁本身变成热点。`sync.Map` 把稳定的那份放进可以用原子读到的 `read`，新键先丢进要加锁的 `dirty`。它像**前台一份不常改的目录，后台一本进货账**：查目录不用排队，账本上的新货多到一定程度，才把账本抄成新目录。

**核心机制**：

```
Load：先原子读 read
        命中 → 返回
        未命中且还有 dirty → 加锁查 dirty，miss 计数 +1
        miss 次数达到阈值 → dirty 晋升为新的 read，dirty 清空
Store 已有键：尽量只改 read 里的条目
Store 新键：加锁写进 dirty
```

1. **适合的三种形态**：键一旦写入就反复读；多个 goroutine 各自写不同的键；缓存、连接注册表这种几乎只增的表。零值可用，不用 `make`。
2. **不适合写多和要一致遍历**：新键不断堆进 dirty，晋升时要整份拷贝，写多了比一把 `RWMutex` 更慢。`Range` 不是某一个时刻的完整快照，也不适合拿它做精确计数。
3. **缓存用 `LoadOrStore`**：它是原子的「有则返回，没有则写入」，避免先 Load 再 Store 的竞态。

**考场口述**：

「`sync.Map` 不是线程安全 map 的通用替换。它内部分 read 和 dirty：read 用原子操作走快路径，适合读；新写入的键放在要加锁的 dirty 里，miss 累积到阈值后把 dirty 晋升成新的 read。所以它适合读多写少、键集合基本稳定的缓存。写频繁、或者要一致地遍历全部键，我会用 `RWMutex` 加普通 map，那时候 `sync.Map` 反而更慢。它的零值可以直接用。」

### 17.nil map、空 map 与 key 的限制

**记忆锚点**：**nil map 能读不能写；key 必须能用 `==` 比较，slice、map、函数都不行**。

**痛点与直觉**：

读一个不存在的键，返回零值，这在 nil map 上也能做，因为「没有这张表」和「表是空的」对查找来说一样。写入要改表的内部结构，nil 没有结构可改，所以 panic。key 则必须能比较：哈希表要判断两个键是不是同一个，slice 的相等要遍历整段元素，和 O(1) 的定位对不上。

**核心机制**：

```
var a map[string]int      nil    读 → 零值    len → 0    写 → panic
b := map[string]int{}     非 nil  可以写
判断「没有元素」用 len(m) == 0，不要用 m == nil

能做 key：布尔、数值、字符串、指针、channel、接口、
         元素可比的数组、字段都可比的 struct
不能：slice、map、func，以及含有它们的 struct
```

1. **空和 nil 都可能 `len == 0`**：只想知道有没有元素，用长度。nil 和空 map 的差别在于能不能写，以及作为返回值时调用方要不要区分「没初始化」和「初始化了但没有数据」。
2. **浮点和接口是两个暗坑**：`NaN != NaN`，用 NaN 做键放得进去、取不出来。接口做键时，比较的是里面的动态值；动态类型是 slice 时，运行时才会 panic。
3. **想用一段字节当键，就先变成 string**：转换会拷贝，换来的是可比较。不要为了省这次拷贝去改 map 的语义。

**考场口述**：

「nil map 和空 map 都能读，读不到就返回零值，`len` 都是 0；只有 nil map 写入会 panic。判断有没有元素用 `len`，不要用和 nil 比较。key 必须可比较：slice、map、函数不行，因为比较它们不是 O(1)，也会让 map 的相等定义变重。数组和结构体可以，前提是元素和字段都能比较。浮点虽然能做 key，但 NaN 不等于自己，放进去就取不出来；接口做 key 时，如果里面装的是不可比较类型，运行时会 panic。」

## string

### 18.🌟string 的底层与不可变性

**记忆锚点**：**string 是 `{只读字节指针, 长度}`；`len` 数的是字节，不是字**。

**痛点与直觉**：

Go 的字符串是 UTF-8 字节序列，不是 UTF-16 的字符数组。不可变带来三件可以直接用的事：多处变量共享同一块字节、能当 map 的 key、并发读不用加锁。代价是每次「修改」都是造一条新的。把它想成**刻好的金属牌**：可以很多人同时看，要改字只能重铸一块。

**核心机制**：

```
string 头：ptr → 只读字节    len = 字节数
"你好"   6 字节，2 个码点
s[0]     第一个字节，不是第一个字
range    下标是字节偏移，值是 rune
s[:3]    切的是字节，可能把一个汉字切成半个
[]byte(s) 和 string(b) 默认各拷贝一次
```

1. **头只有两个字**：没有 cap。和 slice 一样，赋值只复印头，多个 string 可以共享底层字节，因为谁也不能写。
2. **下标、长度、range 用的不是同一把尺子**：`len` 和切片按下标走字节；`range` 按码点解码。字符数用 `utf8.RuneCountInString`，它不分配；`len([]rune(s))` 会先分配。
3. **和 `[]byte` 互转要拷贝**：编译器对 `m[string(b)]` 这类只把字节当 key 查一次的场景可以省掉拷贝，但这是优化，不是语言保证。业务里不要假设转换是零拷贝。

**考场口述**：

「Go 的 string 底层是指向只读字节数组的指针加长度，内容不可变，所以能共享、能当 map 的 key、并发读不用锁。`len` 是字节数，`你好` 的长度是 6。下标取出的是字节，`range` 得到的是码点，按下标切片可能把一个汉字切坏。和 `[]byte` 互转一般会拷贝；编译器只在少数只读场景里消除这次拷贝，不能当成语言规则。」

### 19.string 的拼接与长度

**记忆锚点**：**少量用 `+`，循环里用 `strings.Builder` 并先 `Grow`；`+` 在循环里是平方级拷贝**。

**痛点与直觉**：

字符串不能原地改。`a + b` 要分配一块新内存，把两边都抄进去。放进循环，第 n 次要把前面越来越长的结果再抄一遍，总拷贝量是 O(n²)。`Builder` 内部是一块可增长的字节缓冲，写完一次再变成 string。

**核心机制**：

```
少量、个数固定        +
要格式化              fmt.Sprintf（有反射，不要进热点循环）
已有 []string         strings.Join
循环拼接              strings.Builder，先 Grow
二进制读写            bytes.Buffer
```

1. **`Builder` 先算容量**：`Grow(n)` 一次分够，避免中途扩容再拷贝。`String()` 之后再继续写可以，但不要复制 `Builder` 这个值，它内部有复制检查，复制后写入会 panic。
2. **`Builder` 不做读**：它只负责拼字符串，比 `Buffer` 少一个读下标。既要读又要写、或者内容是二进制，用 `bytes.Buffer`。
3. **`len` 仍然是字节**：拼接前估容量时，中文要按字节算，不能按字数乘 1。

**考场口述**：

「`len(s)` 是字节数。拼接上，固定几段用加号就行；循环里用加号每次都分配并拷贝越来越长的结果，是平方级的。循环拼接用 `strings.Builder`，能预估长度就先 `Grow`。它不能复制，复制后写入会 panic。`fmt.Sprintf` 带反射，不放进热点循环；已经有字符串切片就用 `strings.Join`；要来回读写二进制再用 `bytes.Buffer`。」

## 方法与接口

### 20.🌟值接收者和指针接收者

**记忆锚点**：**值的方法集只有值接收者；指针的方法集两者都有。放进接口时，编译器不会自动取地址**。

**痛点与直觉**：

调用 `d.Speak()` 时，如果 `d` 是可寻址的值，编译器可以偷偷改成 `(&d).Speak()`。一旦把 `d` 放进接口，接口里只保存一份拷贝和类型，没有「原来那个变量」可以取地址。所以同样一个指针接收者方法，变量上能调，赋给接口却编译失败。

**核心机制**：

```
T  的方法集：值接收者
*T 的方法集：值接收者 + 指针接收者

func (d *Dog) Speak() {}
var s Speaker = &Dog{}   // 通过
var s Speaker = Dog{}    // 编译失败
d := Dog{}; d.Speak()    // 可以，编译器取地址
```

1. **接口看的是方法集，不是「变量上能不能点出来」**：点调用有自动取地址；接口赋值没有。这是「明明能调用，一赋给接口就报错」的原因。
2. **指针接收者三条，占一条就用指针**：要改接收者、结构体大、这个类型里已经有别的指针接收者。混用会导致有的方法只在 `*T` 上存在，接口时而能装、时而不能装。
3. **值接收者表达「不修改」**：类型只有几个字、拷贝便宜，并且希望值和指针都能放进接口时，用值接收者。方法集是包含关系，值接收者方法指针类型也有。

**考场口述**：

「值类型 T 的方法集只有值接收者方法，指针类型两者都有。所以指针接收者的方法，变量在可寻址时能直接调，编译器会取地址；但把值放进接口不会自动取地址，`Dog{}` 不能赋给只被 `*Dog` 实现的接口。选择上，要修改、结构体大、或者类型里已经有指针接收者，就统一用指针接收者，不要混用。值接收者适合小结构体，并且值和指针都能满足接口。」

### 21.🌟接口的底层结构与 nil 陷阱

**记忆锚点**：**接口是「类型指针 + 数据指针」；两个都空才是 nil。只往里装一个 nil 指针，接口不是 nil**。

**痛点与直觉**：

`error` 是接口。函数里 `var e *MyErr = nil; return e`，你以为返回的是空错误，调用方 `err != nil` 却成立，接着一点方法还可能 panic。因为盒子上已经贴了类型标签 `*MyErr`，标签在，盒子就不是空的，尽管盒子里的指针是 nil。

**核心机制**：

```
空接口 eface：  _type + data
有方法 iface：  itab  + data
itab 里：接口类型、具体类型、方法地址表

var e *MyErr = nil
return e          // 接口的类型 = *MyErr，数据 = nil
f() == nil        // false

类型相同且数据相同 → 接口相等
数据是 slice / map / func → 比较会 panic
```

1. **返回错误时，nil 指针不要直接当 error 返回**：先判断具体指针是不是 nil，是就 `return nil`，让接口的类型和数据都空。这是这个坑的标准修法。
2. **调用和比较走的不是同一条信息**：方法调用用 itab 里的方法表，所以类型在、数据是 nil 时仍会进方法，方法里再解引用字段就 panic。比较则要求动态类型相同且动态值可比较。
3. **itab 会缓存**：同一种「接口类型 + 具体类型」的方法表算一次，放进运行时的全局表，后面的转换直接复用。

**考场口述**：

「接口值是一对指针。空接口是类型信息加数据，带方法的接口是 itab 加数据，itab 里有方法表。只有类型和数据都是 nil，接口才等于 nil。经典坑是返回 `error` 时，具体变量是一个 nil 的 `*MyErr`：放进接口后类型不是 nil，所以 `err != nil`，但数据指针是 nil，方法里一解引用就 panic。修法是具体指针为 nil 时显式 `return nil`。接口比较还要求动态值可比较，里面装了 slice、map 或函数，比较会 panic。」

### 22.🌟Go 的接口为什么是隐式的

**记忆锚点**：**谁使用谁定义；方法集对上就算实现，不写 `implements`**。

**痛点与直觉**：

Java 的 `implements` 让「查找谁实现了这个接口」很容易，但也要求接口先存在，第三方类型想满足你的接口就得改它的源码。Go 把接口放在使用方：我只需要 `Read`，我就声明一个只有 `Read` 的接口，别人的 `*File` 自动算实现。接口小，才组合得动。

**核心机制**：

```go
type Reader interface {
    Read(p []byte) (int, error)
}
var r Reader = os.Stdin          // *File 不用声明自己实现了 Reader

var _ Reader = (*File)(nil)      // 编译期断言：没实现就编译失败
```

1. **实现关系由方法集决定**：不用在类型上登记。好处是接口可以后写，也可以套在别人的类型上。代价是「这个类型到底满足哪些接口」不能靠一个关键字搜，要靠编译器和方法集。
2. **接口定义在使用它的包**：谁需要这个能力谁声明。一个包又导出接口、又在同包给出唯一实现，通常是把 Java 的继承结构搬过来了。标准库的 `io.Reader` 只有一个方法，大接口由小接口嵌入而成。
3. **`any` 是 `interface{}` 的别名**：Go 1.18 加上的，完全等价。1.18 对接口的真正增强是泛型约束用的类型集合，不是 `any` 这个名字本身。

**考场口述**：

「Go 的接口是隐式实现的，不需要 `implements`，方法集对上就行。接口习惯定义在使用方，这样可以事后抽出来，也可以套到改不了源码的第三方类型上。代价是不能靠一个关键字找到所有实现，所以会在实现旁边写 `var _ Reader = (*File)(nil)` 做编译期检查。`any` 只是 1.18 给 `interface{}` 起的别名。1.18 真正和接口相关的变化是泛型约束：接口可以写类型集合，不只是方法集合。」

**面经**：

- 腾讯 · 校招一面：1.18 之后 interface 有什么增强。https://segmentfault.com/a/1190000045455181

## 错误处理

### 23.🌟`error` 是什么，为什么 Go 不用异常

**记忆锚点**：**`error` 是只有 `Error() string` 的接口；失败是返回值，调用方必须看见**。

**痛点与直觉**：

异常的问题不是慢，是控制流藏起来了：一个函数可能在你没写 `try` 的地方把栈拆掉。Java 用受检异常把「会抛什么」写进签名，签名就长了。Go 把失败放进最后一个返回值，`if err != nil` 啰嗦，但每一处失败都在源码里看得见。社区讨论过类似 `?` 的 `try` 提案，没有采纳。

**核心机制**：

```go
type error interface { Error() string }

data, err := os.ReadFile(path)
if err != nil {
    return fmt.Errorf("read %s: %w", path, err)
}
```

1. **谁实现 `Error() string` 谁就是错误**：惯用最后一个返回值。静态文本用 `errors.New`，要插值用 `fmt.Errorf`，要保留原始错误用 `%w`。
2. **文案是拼出来的**：不要大写开头，不要句号，因为上层还会再包一层。不要用 `_` 把 `err` 丢掉，除非这处失败在注释里写明为什么可以忽略。
3. **可预期的失败不用 panic**：文件没有、网络超时、参数不合法，都是 `error`。panic 留给进程已经不能继续的状态，下一节再分。

**考场口述**：

「`error` 是一个接口，只有 `Error() string`。Go 不用异常做业务失败，是为了让控制流显式：失败就是最后一个返回值，调用方不处理就在代码里看得见。静态文本用 `errors.New`，需要上下文用 `fmt.Errorf`，要保留错误链用 `%w`。错误字符串不大写、不加点，方便被上层拼接。可预期的失败返回 error，不 panic。」

### 24.🌟错误的包装与判定

**记忆锚点**：**`%w` 把错误串成链；`Is` 找哨兵，`As` 拿出某种类型。不要用 `==`**。

**痛点与直觉**：

每一层都想加上自己的上下文：「读配置失败」里面是「连数据库失败」。如果只把文字拼进新的 `errors.New`，上层就认不出原始的 `ErrNotFound`。`%w` 是在新错误上留一截绳子，指向原来的错误。`==` 比的是这一截新对象，绳子另一头它看不见。

**核心机制**：

```go
return fmt.Errorf("find %d: %w", id, ErrNotFound)
errors.Is(err, ErrNotFound)     // 沿 Unwrap 找哨兵
errors.As(err, &target)         // 沿链找类型，并赋给 target
fmt.Errorf("... %v", err)       // 只有文字，链断了
```

1. **`%w` 和 `%v` 差在 `Unwrap`**：`%v` 格式化完就断链，`Is` 和 `As` 走不回去。Go 1.20 起一条 `fmt.Errorf` 可以写多个 `%w`，查找时每个分支都走。
2. **自定义类型要接入链，就实现 `Unwrap() error`**：然后 `Is` 和 `As` 才能穿过它。哨兵错误是包级 `var ErrX = errors.New(...)`，适合表示一种稳定的失败原因；要带字段的失败用结构体，用 `As` 取出来。
3. **`==` 只对没被包装的哨兵成立**：包装后是新的值，地址不同。既然包装是常态，判断统一用 `Is` 和 `As`。

**考场口述**：

「Go 1.13 起用 `%w` 包装错误，新错误通过 `Unwrap` 指回原来的错误。判断用 `errors.Is` 沿链找哨兵，用 `errors.As` 沿链找某个具体类型并取出来。`%v` 只留下文字，链是断的。1.20 之后一个 `fmt.Errorf` 可以有多个 `%w`。自定义错误只要实现 `Unwrap() error` 就能进这条链。包装之后不能用等号比较，因为那是一个新值。」

### 25.🌟`panic` 和 `recover`

**记忆锚点**：**`recover` 只救当前 goroutine、且必须写在 `defer` 里；别的 goroutine 的 panic 带走整个进程**。

**痛点与直觉**：

`panic` 是「这条路已经走不通了」，不是「这次请求失败了」。它把当前函数停掉，先把本函数的 defer 倒着跑完，再往上抛。`recover` 像只装在这一节车厢里的刹车：刹车不在这节车厢，或者没装在 defer 这块规定的位置上，就刹不住。子 goroutine 是另一列车，它出轨时整趟进程一起停。

**核心机制**：

```
panic
  → 当前函数停住，defer 按 LIFO 执行
  → defer 里 recover 到了：拿到 panic 值，本函数正常返回
  → 没有 recover：继续往调用方抛
  → 这个 goroutine 最外层还没有：进程退出

抓不住的：
  别的 goroutine 的 panic
  不在 defer 里的 recover
  runtime.throw：并发写 map、栈溢出、内存耗尽
```

1. **每个 `go` 自己装 defer**：库里启动 goroutine 时，入口包一层 `defer recover`，把堆栈记下来再决定重启还是退出。只在 main 里 recover，护不住工人 goroutine。
2. **recover 之后数据可能改了一半**：它适合「记下日志，结束这个请求或拉起新的 goroutine」，不适合假装没事继续用改到一半的结构。
3. **什么该 panic**：启动时缺了无法运行的配置、明确写了不可能到达的分支、进程级初始化失败。参数错误、文件不存在、业务规则不满足，都返回 error。

**考场口述**：

「panic 是不可恢复的程序故障，业务失败用 error。recover 有两个硬条件：必须在 defer 里调用，并且只能接住当前这个 goroutine 的 panic。子 goroutine 没人 recover，整个进程退出。还有一类根本不是 panic，并发写 map、栈溢出走的是 `throw`，recover 也抓不住。recover 之后我只做日志和隔离，不继续使用可能改了一半的状态。」

**面经**：

- 腾讯 · 校招一面：外层协程能不能捕获子协程的 panic；哪些 panic 捕获不了。https://segmentfault.com/a/1190000045455181
- 字节 · 后端一面：匿名函数里 panic，外面的 defer 能不能 recover，反过来呢。https://www.nowcoder.com/discuss/648273029868400640

### 26.🌟`defer` 的执行时机

**记忆锚点**：**入栈时参数就算完，出栈时按后进先出跑；闭包改的是命名返回值**。

**痛点与直觉**：

`defer` 用来保证不管从哪条 return 出去，资源都会关。它替掉了 `try-finally`。容易错的是时间点：你写 `defer fmt.Println(n)` 时，`n` 在这一行就已经抄进参数了，不是等函数返回才去读。闭包不抄值，它抓住的是变量本身，所以能在返回前改掉命名返回值。

**核心机制**：

```go
func f() (n int) {
    defer fmt.Println(n)       // 注册时 n 是 0，打印 0
    defer func() { n++ }()     // 执行时 n 已经是 1，返回值变成 2
    return 1                   // 先把 1 写入命名返回值 n，再跑 defer
}
多个 defer：后注册的先执行
```

1. **三步顺序**：把返回值写好，然后 LIFO 执行 defer，然后真正离开函数。所以 defer 里的闭包看得到 `return` 刚写上的命名返回值，也能再改它。没名字的返回值，闭包够不着。
2. **参数和闭包是两种捕获**：`defer f(n)` 的 `n` 立刻求值；`defer func(){ use(n) }()` 里的 `n` 是执行时的值。循环里 `defer fmt.Println(i)` 会印出 2、1、0，因为每次注册时 `i` 已经抄进去了。
3. **循环里不要把 defer 堆到外层函数**：文件多了，句柄要等整个函数返回才关。在循环里包一层函数，让 defer 在这一轮结束就跑。Go 1.14 起非循环路径的 defer 是开放编码，开销很小，不用为了性能避开它。

**考场口述**：

「defer 在函数返回前执行，多个是后进先出。参数在 defer 这行注册时就求值，不是执行时才读；闭包捕获的是变量，执行时才看当前值。命名返回值的顺序是：先把 return 的值写进返回值变量，再跑 defer，所以 defer 里的闭包可以改返回值，这也是包装 error 的常用写法。循环里打开的文件不要 defer 到外层，否则句柄会堆到函数结束；包一层立即执行的函数，让它在每一轮关掉。1.14 之后普通 defer 是开放编码，不用为了性能刻意不用。」

## 泛型

### 27.🌟Go 泛型怎么用，和 Java 差在哪

**记忆锚点**：**1.18 起用类型参数，约束是接口的类型集合；编译期实例化，不是擦除，也没有泛型方法**。

**痛点与直觉**：

没有泛型时，一个 `Sum` 要为 `[]int` 和 `[]float64` 各写一遍，或者收 `[]any` 再断言，断言把类型错误推到运行时。Go 的做法是编译时按实参各生成一份代码，基本类型不用装箱。它不像 C++ 模板那样什么都能做，约束必须写在接口里，编译器拒绝约束之外的运算。

**核心机制**：

```go
type Number interface { ~int | ~int64 | ~float64 }
func Sum[T Number](xs []T) (total T) { /* total += x */ }

type Stack[T any] struct { items []T }
func (s *Stack[T]) Push(v T) {}     // 类型参数在类型上，不在方法上
```

1. **和 Java 的三处差别**：Java 擦除，运行时看不到 `T`，基本类型要装箱；Go 编译期实例化，`int` 就是 `int`。Java 有泛型方法；Go 的方法不能再引入自己的类型参数，参数必须放在接收者的类型上。
2. **`~` 表示底层类型**：`type MyInt int` 的底层是 `int`，`~int` 能接住它，单独写 `int` 则不行。
3. **实例化会增加代码量**：同一份函数按不同类型各有一份，编译变慢、二进制变大。标准库用它做 `slices`、`maps` 这种容器算法；业务里能用小接口说清的，不必上泛型。

**考场口述**：

「Go 1.18 引入类型参数，约束写成接口，里面可以是类型联合，`~T` 表示底层类型是 T。和 Java 的差别我记三点：Go 是编译期实例化，不是类型擦除，所以 int 不用装箱；没有协变，`[]int` 和 `[]int64` 没有关系；方法不能声明自己的类型参数，要写在接收者类型上，比如 `Stack[T]` 的 `Push`。每个类型会生成一份代码，所以泛型适合通用容器和算法，不是所有业务抽象的默认选项。」

### 28.泛型约束的写法

**记忆锚点**：**约束就是接口：类型联合、方法集、`comparable` 三种，类型集合和方法集不要混写**。

**痛点与直觉**：

类型参数如果完全自由，函数体里就什么运算都不能做，因为编译器不知道 `T` 有没有 `+` 或 `==`。约束是一份允许清单：清单上可以写「必须是这些类型之一」，也可以写「必须有这些方法」。一份接口里把两种清单混在一起，读的人无法判断一个类型要怎样才算满足，所以语言直接禁止，`comparable` 是预声明的例外。

**核心机制**：

```go
type Number interface { ~int | ~int64 | ~float64 }  // 类型集合
type Stringer interface { String() string }         // 方法集
func Contains[T comparable](xs []T, v T) bool       // 可以用 ==
// 现成的：cmp.Ordered、slices / maps 包里的约束
```

1. **`comparable` 是能 `==` 和 `!=` 的类型集合**：写查找、做 map 的 key 约束时用它。它是预声明标识符，不是你自己能用联合类型仿出来的全部可比较类型。
2. **一个接口里不要既写 `|` 又写方法**：类型集合是「这些类型」，方法集是「有这些行为」。`comparable` 可以和普通方法接口相交，那是语言给的特例，不是自己混写的理由。
3. **优先用标准库的约束**：排序用 `cmp.Ordered`，不要在每个项目里重写一遍整数加字符串的联合。

**考场口述**：

「约束就是接口，有三种写法：用 `|` 写类型联合，用方法写行为，用预声明的 `comparable` 表示能做等号比较。`~` 放在类型前面，表示接受这个底层类型的自定义类型。同一个接口里不要把类型联合和方法混在一起，`comparable` 是例外。业务里能用 `cmp.Ordered` 或 slices 包的，就不要自己再声明一套。」

### 29.`go` 关键字与 goroutine 等待

**记忆锚点**：**`go f()` 只负责把任务交出去；main 一返回，其他 goroutine 全部被掐掉**。

**痛点与直觉**：

`go` 不保证函数已经开始跑，更不保证跑完。主 goroutine 像**会场的总电闸**：闸拉掉时，分会场里还在发言的人不会被等。所以「我明明 go 出去了，日志却没打」的第一反应不该是调度器丢了任务，而是主函数先退出了。

**核心机制**：

```go
var wg sync.WaitGroup
for i := 0; i < n; i++ {
    wg.Add(1)                 // 必须在 go 之前
    go func() {
        defer wg.Done()
        work()
    }()
}
wg.Wait()
```

1. **`Add` 在 `go` 之前**：如果在新 goroutine 里面 `Add`，`Wait` 可能先看到计数为 0 直接返回。计数减到负数会 panic。
2. **等待方式就这一条语义**：`WaitGroup` 适合一组任务都完成；需要结果或取消时用 channel 和 `context`，那部分在并发篇。`GOMAXPROCS` 决定有多少个逻辑处理器同时跑 Go 代码，默认是机器核数，它不改变「main 退出就全停」。
3. **闭包传参和循环变量是两件事**：任务函数要的参数，作为实参传进去。循环变量本身的新旧语义看下一节，不要和 `WaitGroup` 混成一个坑。

**考场口述**：

「`go` 把函数交给调度器就返回，不阻塞，也不保证立刻执行。主 goroutine 退出时，其他 goroutine 直接被终止，所以要等它们跑完。`WaitGroup` 的 `Add` 必须发生在 `go` 之前，否则 `Wait` 可能提前返回；`Done` 放在 defer 里。`GOMAXPROCS` 只决定并行度，默认是 CPU 核数，不负责等待。」

**面经**：

### 30.🌟循环变量在 goroutine 里的坑

**记忆锚点**：**1.22 起每次迭代新建循环变量；旧语义是否还在，看 `go.mod` 的 `go` 行，不看编译器版本**。

**痛点与直觉**：

1.22 之前，`for` 里用 `:=` 声明的变量整个循环只有一个，每轮是给它赋新值。goroutine 晚一点才读这个变量，就都读到最后一轮的值。1.22 改成每轮一个新变量，效果相当于循环体开头帮你写了 `v := v`。老模块如果没改 `go` 那一行，编译器再新也仍按旧语义编译。

**核心机制**：

```
go 1.21 及更早的 go 行：一个 v，闭包共享，都看到最后一轮
go 1.22 起：每轮新建 v

仍会共享的写法：
var v string
for _, v = range items {      // 注意是 = ，变量在循环外
    go func() { use(v) }()
}
```

1. **门控在语言版本，不在工具链**：用 Go 1.24 的编译器编译 `go 1.16` 的模块，循环变量仍是旧语义。看到老代码里的 `v := v`，先看 `go.mod`，不要当成多余。
2. **显式声明在循环外的变量不在新语义里**：`:=` 变成每轮新建；循环外的 `var` 再在循环里 `=` 赋值，还是同一个变量。
3. **闭包晚于循环执行就会暴露**：不只有 `go`。把函数存进切片、注册成回调，只要在循环结束后才调用，旧语义下同样拿到最后一个值。

**考场口述**：

「这是有版本分界的题。1.22 之前，`for` 的循环变量整个循环只有一个，闭包和 goroutine 若在循环结束后才读，会全部看到最后一轮。1.22 起每次迭代新建变量，等价于每轮开头 `v := v`。但新语义只对 `go.mod` 里 `go 1.22` 及以上的模块生效，和机器上的编译器版本无关。另外，变量如果声明在循环外面，再用等号赋值，现在也仍然共享。」

## 其他语法

### 31.`switch` 的特殊之处

**记忆锚点**：**默认不贯穿；想落到下一支，必须写 `fallthrough`**。

**痛点与直觉**：

C 和 Java 的 switch 忘了 `break` 会悄悄落入下一支，这种 bug 比少写一个分支更难看见。Go 把安全的行为设成默认：一支做完就结束。要贯穿必须写出来，读代码的人不会猜。

**核心机制**：

```go
switch x := f(); x {          // 可以带初始化语句
case 1, 2, 3:                 // 多个值
case 4:
    fallthrough               // 必须是这一支的最后一行
default:
}

switch {                      // 省略表达式，就按 case 条件从上往下
case x < 0:
}

switch v := i.(type) {        // 类型开关，不能 fallthrough
}
```

1. **三件和 C 不同的事**：默认 break；分号前可以有初始化；表达式可以整个省掉，变成一串条件。
2. **`fallthrough` 不判断下一个 case 的条件**：它直接进入下一支的语句，所以不能用在类型开关里，也必须放在当前支的最后。
3. **类型开关同时完成收窄**：`v := i.(type)` 之后，每个 case 里的 `v` 是那个具体类型。这是第 8 节断言的语法形式，不是普通的值比较。

**考场口述**：

「Go 的 switch 默认不贯穿，一支执行完就结束，要进下一支必须显式写 `fallthrough`，而且它不重新判断下一个 case 的条件，也不能用在类型开关里。switch 可以带短变量声明，也可以省略被判断的表达式，当成一串 if。多个值写成 `case 1, 2, 3`。类型开关是另一件事，用来把接口收窄成具体类型。」

### 32.`unsafe.Pointer` 什么时候用

**记忆锚点**：**`unsafe.Pointer` 是 GC 认得的指针；`uintptr` 只是整数，拿去算完地址必须马上转回来**。

**痛点与直觉**：

类型系统不允许 `*int` 和 `*string` 互换。`unsafe.Pointer` 是唯一可以在任意指针类型之间穿过的类型，像把类型标签暂时揭掉。揭掉之后，布局、对齐、GC 都不替你担保。业务代码出现它，通常是把一个本该在 API 边界解决的问题，钻进了内存布局里。

**核心机制**：

```
*T  ↔  unsafe.Pointer  ↔  *U     合法的跳板，GC 仍追踪
unsafe.Pointer → uintptr         变成整数，可以做加减
uintptr 不保证还指向活着的对象    GC 不把它当指针
算完必须立刻转回 unsafe.Pointer，中间不能有可能发生 GC 的调用
```

1. **两句区分**：`unsafe.Pointer` 是指针，GC 会把它指向的对象当成可达。`uintptr` 是整数，GC 不追踪，对象可能被搬走或回收，整数还留着旧地址。
2. **合法场合就三类**：cgo 和 C 指针互转、序列化里按字段偏移做零拷贝、运行时或标准库这种已经锁死布局的代码。把 string 硬转成 `[]byte` 再写入，会去改只读内存，可能直接段错误。
3. **布局不是兼容承诺**：结构体字段顺序、填充随时可能随版本变化。依赖偏移的代码要有测试，并锁住 Go 版本。日常业务用 slice、`encoding` 和明确的拷贝。

**考场口述**：

「`unsafe.Pointer` 能在不同指针类型之间转换，GC 仍然追踪它。`uintptr` 只是一个整数，GC 不追踪，所以指针转成 uintptr 做偏移计算后要马上转回来，中间不能调用可能触发 GC 的函数。我只在和 C 交互、或者确认过的零拷贝里用它。把 string 转成可变字节切片再写，会改到只读内存。普通业务代码不该出现 unsafe，因为它依赖的内存布局不是语言承诺。」
