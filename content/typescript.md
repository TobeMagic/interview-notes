# TypeScript

对标 Java SE 与集合里属于语言本身的部分。事件循环在浏览器篇，异步 I/O 在 Node 篇。

每一节按大脑记忆四步法编排：**记忆锚点**（一秒抓骨架）→ **痛点与直觉**（为什么这么设计 + 物理类比）→ **核心机制**（空间图解 + 3 个核心组块）→ **考场口述**（30 秒第一人称串词）。

## 概述与编译

### 1.🌟TypeScript 是什么，为什么前端要引入它

**记忆锚点**：**编译期贴封条，运行时撕干净**——TS 是带静态契约的 JS 超集，只管构建时体检，不管线上运行时验货。

**痛点与直觉**：

几百行的表单脚本靠人脑就能记住变量形状；一旦进到几万行、几十人协作的单页应用，纯 JS 就会死在「**没契约**」三个字上：改一个字段名不敢删、函数入参形状全靠猜、接口少吐一个字段直接线上白屏报 `Cannot read properties of undefined`。

把 TS 想象成**施工现场的脚手架与蓝图校验仪**：盖楼（写代码与编译）时它严格比对每根管线的口径对不对得上；大楼交付入住（浏览器运行 JS）前，脚手架全部拆光，住户看到的仍然是纯粹的 JS。

**核心机制**：

```
                   ┌─ 1. 类型检查流 (tsc --noEmit) ──► 建符号表 & 类型图 → 报错拦截
.ts 源码 (超集) ───┤
                   └─ 2. 代码生成流 (esbuild / Vite) ─► 擦除类型标签 + 语法降级 → 纯 .js
```

1. **检查与产出双轨分离**：`tsc` 能只做类型检查不产出文件（`--noEmit`）；反过来 Vite / esbuild 能只剥掉类型标签秒级产出 `.js` 而不做类型检查，所以类型报错默认拦不住打包器启动。
2. **三大基因（结构化、擦除式、图灵完备）**：按形状匹配不看继承名分（结构化）；编译完类型全消失（擦除式）；类型层面能写分支与递归（图灵完备）。
3. **编译期安全 ≠ 运行时安全**：`JSON.parse(raw) as User` 只是给编译器贴免检封条；外部网络接口、`localStorage`、URL 参数进入系统时，必须配合 zod 或类型守卫做运行时验货。

**考场口述**：

「TypeScript 本质上是给 JavaScript 加了一层**编译期的静态契约**，它是 JS 的类型超集，最终产出的依然是普通 JS。我一般从三个维度理解它：第一是**工程收益**，它把原本靠口头约定的参数形状变成编译器可校验的契约，解决了大型项目重构不敢改、IDE 没法补全的痛点；第二是**双轨机制**，类型检查和代码生成是解耦的，所以 esbuild 和 Vite 可以只剥离类型实现秒级启动；第三是**运行时边界**，因为类型在编译后会被擦除，它管不了接口返回的脏数据，外部输入还得靠 zod 或类型守卫做运行时校验。」

### 2.🌟`tsc` 到底做了什么

**记忆锚点**：**五步走流水线，三旋钮定方向**——只管「查类型 + 降语法 + 吐声明」，绝不越界干打包压缩。

**痛点与直觉**：

很多人分不清 `tsc` 和 Webpack / Vite 的边界，以为 `tsc` 也是打包器。其实浏览器只认标准 JS，`tsc` 就像**海关检疫官兼翻译官**：它先把每个包裹开箱验货（类型检查），再把高版本方言翻译成老浏览器能懂的白话（语法降级），附上货物清单（`.d.ts`）；至于把几百个包裹塞进一个集装箱（合包、摇树、压缩、热更新），那是货运公司（Bundler）的活。

**核心机制**：

```
源码 (.ts) ──► [1.Parse 解析 AST] ──► [2.Bind 建符号表] ──► [3.Check 算类型图(最慢)]
                                                                  │
产物 (.js + .d.ts) ◄── [5.Emit 输出] ◄── [4.Transform 按 target 降级语法] ◄─┘
```

1. **五阶段流水线（卡在第三步）**：Parse 转语法树 → Bind 绑作用域符号 → **Check 全局类型推导与兼容校验（耗时占大头）** → Transform 语法降级 → Emit 产出 `.js` 与 `.d.ts`。
2. **三大配置旋钮互不干扰**：`target` 管语法降到哪一年（比如箭头函数转不转 `function`）；`lib` 管环境里认哪些内置类型（比如认不认 `document` 和 `Promise`）；`module` 管输出 ESM 还是 CommonJS。
3. **提速靠剪枝类型图**：因为第 3 步要扫描 `node_modules` 里几千份 `.d.ts`，大项目必开 `skipLibCheck: true` 跳过第三方声明自检，或用 `incremental` / Project References 做增量检查。

**考场口述**：

「`tsc` 核心只做两件事：**全局类型检查**和**单文件级的代码转译**，不做模块合并与 tree shaking。它的内部管线分五步：解析 AST、绑定符号表、全局类型检查、按 `target` 降级语法、最后输出 `.js` 和 `.d.ts`。配置上最容易混的是 `target` 和 `lib`——`target` 决定语法降级到哪个 ES 版本，而 `lib` 决定编译器认识哪些环境 API，两者完全独立。另外因为全局类型检查要扫描所有依赖声明，工程里通常会开启 `skipLibCheck` 和增量编译来解决 `tsc` 慢的问题。」

### 3.TypeScript 的编译器是什么写的

**记忆锚点**：**6.x 前自举跑单核，7.0 起 Go 写吃多核**——命令还是 `tsc`，全量构建快十倍。

**痛点与直觉**：

过去十几年 TS 用自己写自己（自举），跑在 Node.js 上。这就像**用单车道拉货车**：类型检查本来是极度吃 CPU 且天然能多文件并行的重活，但 JS 单线程加 V8 垃圾回收把它死死卡在单核里，大仓库跑一次全量 `tsc` 动辄几分钟。微软在 TypeScript 7.0（2026-07）干脆把编译器一比一移植到了 Go，直接换上了多车道高速路。

**核心机制**：

```
旧版 (≤6.x 自举实现)：TS/JS 源码 ──► Node.js 单线程 + V8 堆限制 ──► 大项目全量检查极慢
新版 (≥7.0 原生端口)：Go 语言移植 ──► 原生机器码 + 共享内存多线程 ──► 全量构建提速 8–12 倍
```

1. **一比一忠实移植（Port 而非 Rewrite）**：7.0 不是重新发明一门语言，而是把原 TS 编译器的 AST 结构与检查逻辑原封不动搬到 Go，保证类型推断结果与旧版一致，业务代码零改动升级。
2. **原生机器码 + 共享内存并发**：Go 编译成原生二进制，没有 JIT 预热开销，且多个 goroutine 能直接共享内存里的符号表与类型图，把多核 CPU 吃满。
3. **旧管线遗产的兼容边界**：安装方式仍是 `npm i -D typescript`，编辑器改走标准 LSP 协议；唯一需要留意的是重度依赖旧编译器内部管线的特性（如 NestJS 依赖的 `emitDecoratorMetadata`），升级前需核对官方发行说明。

**考场口述**：

「这是一个有版本分界的时效题。在 6.x 之前，TypeScript 编译器是用 TS 自己写的自举实现，跑在 Node.js 上；从 **TypeScript 7.0** 开始，官方正式切换到了用 **Go 语言一比一移植的原生编译器**，命令和 npm 安装方式都没变，但全量构建速度提升了 8 到 12 倍。之所以用 Go 重写，是因为类型检查属于 CPU 密集型任务，原来的 JS 单线程无法利用多核共享内存并发。需要注意的是，这次是忠实移植而非语法改版，主要收益都在编译与 IDE 响应速度上。」

### 4.🌟什么是类型擦除

**记忆锚点**：**过河拆桥不留痕，运行之时无类型**——`interface`、`type`、泛型全蒸发，`new T()` 和 `instanceof 接口` 必报错。

**痛点与直觉**：

浏览器里的 V8 引擎只认得 JS，根本不认识什么 `interface User` 或泛型 `<T>`。如果 TS 要在运行时保留类型，全世界所有浏览器都得跟着改引擎。所以 TS 采用了「**隐形墨水**」策略：写代码和过安检时字迹清清楚楚，一旦编译成 `.js` 交付上线，所有类型墨水全部蒸发，一行运行时代价都不留。

**核心机制**：

```
【编译期 .ts】  interface User { name: string }
               function id<T>(x: T): T { return x }
                         │
                         ▼  类型擦除 (Type Erasure)
【运行时 .js】  function id(x) { return x }   // User 与 <T> 彻底蒸发，零运行时开销
```

1. **四大禁区由此诞生**：因为运行时没有类型，所以**不能 `new T()`**（`T` 已蒸发，需改传构造函数 `ctor: new () => T`）、**不能 `instanceof SomeInterface`**、**不能读 `T.name`**、**不能对类型用运行时的 `typeof`**。
2. **零运行时性能损耗**：擦除意味着 TS 类型系统不会往产物里塞任何额外校验代码，编译出来的 JS 和手写 JS 跑得一模一样快。
3. **同名 `typeof` 的阴阳两界**：写在类型位置（`type A = typeof obj`）是编译期查静态形状，编译完就蒸发；写在值位置（`if (typeof obj === 'object')`）是 JS 原生算符，会留在产物里跑。

**考场口述**：

「类型擦除指的是 TS 在编译成 JS 的过程中，会把 `interface`、`type`、类型标注和泛型参数**全部抹掉**，产物里不留任何类型信息。理解了擦除，就能顺推出它的三个核心结论：第一，TS 是**零运行时开销**的，不会拖慢线上执行速度；第二，任何试图在运行时读取静态类型的操作都会失败，比如不能写 `new T()` 或 `x instanceof MyInterface`，真要实例化泛型必须把构造函数当成值传进来；第三，要在运行时做类型判断，只能靠手写类型守卫，或者走装饰器元数据那套额外机制。」

### 5.哪些 TS 语法不会被擦除

**记忆锚点**：**枚举空间参数饰，四大异类留真身**——`enum`、`namespace`、参数属性、装饰器会生成真实 JS 代码。

**痛点与直觉**：

在 TS 早期（ES6 还没普及的年代），为了补齐 JS 缺少的工程能力，TS 团队不仅加了「隐形墨水」（纯类型），还顺手加了四样「**实体补丁**」。这四样东西表面长得像类型语法，编译后却会往 `.js` 里塞入实打实的对象和函数调用——就像拆脚手架时留下的四根承重柱，不仅占包体积，还会干扰单文件剥类型的打包器。

**核心机制**：

```
┌───────────────────────────┬──────────────────────────────────────────┐
│ TS 源码 (看似类型/语法糖)  │ 编译后的真实 JS 产物 (留在运行时)        │
├───────────────────────────┼──────────────────────────────────────────┤
│ enum Color { Red }        │ 立即执行函数 (IIFE) + 双向映射对象       │
│ namespace N { ... }       │ 立即执行函数 (IIFE) 挂载闭包对象         │
│ constructor(private x)    │ 构造函数体内自动插入 this.x = x          │
│ @Log class A {}           │ __decorate([...], A) 运行时包装调用      │
└───────────────────────────┴──────────────────────────────────────────┘
```

1. **为什么大厂规范普遍禁用 `enum`**：一来它生成双向映射 IIFE 占体积、阻断 tree shaking；二来 `const enum` 内联需要跨文件读取定义，在 Vite / esbuild 的单文件转译（`isolatedModules`）下跨包必崩；三来数值枚举允许任意数字混入。标准替代方案是 **`as const` 对象 + `typeof` 提取联合类型**。
2. **`namespace` 已被 ESM 取代**：它是模块化标准出台前的产物，现代工程一律用 `import / export`，只在维护古老 `.d.ts` 全局声明时才会碰到。
3. **参数属性与装饰器服务于 DI 框架**：`constructor(private readonly svc: Svc)` 和 `@Injectable()` 是 NestJS 等依赖注入框架的命根子，在后端 TS 中仍广泛保留，但在纯前端组件里尽量少用。

**考场口述**：

「虽然 TS 主打类型擦除，但有**四个历史例外**会生成真实的运行时 JS 代码，分别是 **`enum` 枚举、`namespace` 命名空间、构造函数参数属性、以及装饰器**。面试和工程里最常考的是为什么要避开 `enum`：因为它不仅会编译成一段双向映射的立即执行函数增加包体积，而且 `const enum` 在 Vite、esbuild 这种单文件转译工具开启 `isolatedModules` 时没法跨包内联。所以现在主流规范都用 **`as const` 常量对象配合 `keyof typeof`** 来替代枚举，既保留了运行时对象，又拿到了严密的字面量联合类型。」

### 6.🌟闭包是什么，为什么它是 Hooks 的基础

**记忆锚点**：**栈帧已散魂还在，外层变量背囊中**——函数出生时背走了外层词法环境的引用包，只要函数不死，包里变量不收。

**痛点与直觉**：

正常情况下，函数执行完、栈帧一弹出，里面的局部变量就该灰飞烟灭。但前端到处是「**现在定义、将来才调**」的场景：定时器、按钮点击回调、防抖节流、React 的 `useState`。如果外层函数一跑完变量就销毁，将来的回调拿什么干活？

把闭包想象成**远行者背上的登山包（`Context` 对象）**：当内部函数在父函数里出生时，V8 编译器做了一次逃逸分析，把内部函数将来要用的那几个外层变量从临时栈帧里拎出来，塞进堆上的专属登山包里挂在函数身上。父函数哪怕早就退场了，只要这个子函数还活着，它随时能伸手进包里摸出当年的变量。

**核心机制**：

```
【外层函数执行期 (栈帧)】              【外层函数返回后 (堆内存 Context)】
 ┌────────────────────┐               栈帧已销毁，但逃逸变量留在堆包里：
 │ counter() 栈帧     │                 ┌──────────────────────────┐
 │   let n = 0  ──────┼── 逃逸搬移 ───► │ Closure Context { n: 0 } │ ◄──┐
 │   return () => ++n │                 └──────────────────────────┘    │
 └────────────────────┘                                                 │
                                        const c = counter() ────────────┘
                                        (函数实例持有 [[Environment]] 指针)
```

1. **产生条件与逃逸本质**：只要内部函数引用了外层作用域的变量，并且该函数被返回或传到了别处，被捕获的变量就会从栈逃逸到堆上的 `Context` 环境对象中。
2. **两大经典踩坑（循环共享与内存泄漏）**：`for (var i...)` 只有一个函数级变量 `i`，三个异步回调背的是同一个包（全打 3），换 `let` 才每轮发一个新包；如果事件监听或全局变量长期抓住闭包不放，包里的巨型对象（如 DOM 节点或大数组）就永远无法被 GC 回收。
3. **React Hooks 的旧值陷阱根源**：函数组件每次渲染都是独立的一轮函数调用，当次渲染的 `state` 是那次包里的常量；如果 `useEffect` 或定时器没更新依赖，它抓着的永远是第一轮渲染那个旧背包里的旧值。

**考场口述**：

「闭包本质上是**词法作用域的副产物**：当一个内部函数访问了外层函数的变量，并在外层函数执行完后依然存活，V8 就会通过逃逸分析把这些被引用的变量放到堆上的 `Context` 对象里，让函数一直背着走。在工程里它主要有三面：正面是用来做**私有状态封装、防抖节流和柯里化**；反面是如果全局事件监听或定时器忘了销毁，闭包拽着的大对象就会造成**内存泄漏**；而在 React 里，因为每次渲染都有独立的闭包作用域，漏写 Hook 依赖就会读到旧背包里的陈旧 `state`，也就是常说的闭包陷阱。」

### 7.🌟`this` 到底指向谁

**记忆锚点**：**普通函数看调用点（new > 显绑 > 点调 > 裸调），箭头函数看出生点**。

**痛点与直觉**：

闭包里的变量看的是「**函数在哪出生**」（词法作用域），唯独普通函数的 `this` 反其道而行之，看的是「**函数被谁喊了一声**」（动态绑定）。这就好比同一份租房合同，谁在上面签字画押（调用点前缀），房东（`this`）就是谁；一旦你把方法从对象上撕下来单独调（`const f = obj.hi; f()`），签名人没了，`this` 当场丢失变成 `undefined`。为了治好这个毛病，ES6 才引入了根本没有自己 `this` 的箭头函数。

**核心机制**：

```
                     调用一个函数时，this 是谁？
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼ 是箭头函数 () => {}                           ▼ 是普通函数 function
 【词法 this：看出生点】                         【动态 this：按 4 级优先级漏斗判定】
 本身无 this 槽位，直接往外层作用域找             1. new Fn()        ──► 新建的实例对象
 （bind / call / apply 对它完全无效，            2. call/apply/bind ──► 显式传入的第 1 参数
   且没有 prototype、不能 new）                  3. obj.fn() 点调用 ──► 点号左边的 obj
                                                 4. fn() 裸调用     ──► 严格模式 undefined / 非严格 window
```

1. **普通函数四级优先级**：**`new` 构造 > `call / apply / bind` 显式绑定 > `obj.fn()` 隐式点调用 > `fn()` 默认裸调**。注意一旦经过 `bind` 硬绑定，外层已经包死，后面再接 `.call()` 也改不掉它的 `this`。
2. **`call / apply / bind` 三兄弟分工**：`call(thisArg, a, b)` 逐个传参立即跑；`apply(thisArg, [a, b])` 数组传参立即跑；`bind(thisArg, a)` 只打包返回新函数、不立即执行。
3. **箭头函数的三无特性**：**无自己的 `this`**（沿外层词法作用域继承）、**无 `arguments` 对象**、**无 `prototype` 与 `[[Construct]]`**（因此绝对不能用 `new` 调用）。

**考场口述**：

「判断 `this` 我一般先分阵营：**普通函数看调用方式，箭头函数看定义位置**。普通函数遵循四级优先级漏斗：最高是 `new` 调用指向新实例；第二是 `call`、`apply`、`bind` 显式指向传入的第一个参数，其中 `bind` 返回新函数且一旦绑死不可再改；第三是 `obj.fn()` 点调用指向点前面的对象；最低是裸调用，在 ESM 和 TS 编译后的严格模式下都是 `undefined`。而箭头函数本身根本没有 `this` 槽位，也不支持 `new` 和 `bind` 改指向，它永远直接拿定义时所在外层作用域的 `this`。」

### 8.🌟原型链是什么

**记忆锚点**：**实例靠 `__proto__` 往上认祖宗，函数靠 `prototype` 备好传家宝，查到 `null` 算到头**。

**痛点与直觉**：

如果你用构造函数 `new` 出一万个用户实例，每个实例都要调 `.say()` 方法——要是把这个函数复制一万份塞进每个对象里，内存当场就爆了。JS 的解法不是造一套复杂的「类模板」，而是搞了一套「**共享物资站（原型对象）+ 向上委托链**」：每个实例兜里只揣自己的私有数据（如 `name`），再栓一根绳子（`[[Prototype]]` / `__proto__`）指向公共物资站（`Fn.prototype`）。自己兜里翻不到的属性，就顺着绳子去上一级物资站找，一路找到 `Object.prototype` 还不见，撞上终点的 `null` 就返回 `undefined`。

**核心机制**：

```
实例 p ──.__proto__──► Person.prototype ──.__proto__──► Object.prototype ──.__proto__──► null
  ▲                         ▲
  └─── new Person() ────────┴─── Person.prototype (函数独有的属性，存放共享方法)
```

1. **分清两个高频易混词**：`prototype` 是**构造函数独有**的普通属性，相当于「给未来儿孙准备的共享物资库」；`[[Prototype]]`（通过 `Object.getPrototypeOf(obj)` 或 `obj.__proto__` 访问）是**每个对象实例都有**的向上查找链表指针。
2. **`new Fn()` 的四步标准动作**：① 造一个空对象 `{}` → ② 把空对象的 `[[Prototype]]` 挂到 `Fn.prototype` 上 → ③ 把 `this` 指向该对象并执行 `Fn` 赋初值 → ④ 若 `Fn` 显式返回了引用对象则用它，否则返回刚才造的新对象。
3. **工程延伸（无原型字典与 ES6 `class`）**：ES6 `class` 只是原型链的语法糖（方法默认不可枚举、强制严格模式、必须用 `new` 调）；而工程里做纯键值哈希表时常用 `Object.create(null)` 造一个**断掉原型链的净空对象**，防止用户输入 `"toString"` 或 `"__proto__"` 触发原型污染。

**考场口述**：

「原型链本质上是 JS 实现对象方法复用和继承的**向上委托查找机制**。每个对象内部都有一个 `[[Prototype]]` 隐式引用（也就是 `__proto__`），而每个构造函数都有一个 `prototype` 属性用来挂载共享方法。当通过 `new` 创建实例时，实例的隐式原型就会指向构造函数的 `prototype`。访问对象属性时，引擎先查对象自身，找不到就顺着这条链往上找，直到 `Object.prototype` 再往上的 `null` 为止。工程上 `instanceof` 就是顺着这条链判断右边构造函数的 `prototype` 在不在左边对象的原型链上；另外做纯净字典映射时，我们会用 `Object.create(null)` 切断原型链来防原型污染。」

### 9.基本类型和引用类型

**记忆锚点**：**基本类型存值在栈（各改各的），引用类型存址指堆（牵一发动全身）**。

**痛点与直觉**：

很多线上诡异 bug——比如「明明只改了弹窗表单里的临时变量，结果列表页原数据跟着变了」——全是因为没分清变量盒子里装的到底是「**现钞（值本身）**」还是「**保险柜钥匙（堆内存地址）**」。给别人复制一份现钞，他烧了也不影响你；给别人配一把同一只保险柜的钥匙，他开门换了里面的东西，你打开看自然也变了。

**核心机制**：

```
【栈内存 (Stack / 寄存器)】                    【堆内存 (Heap)】
  let a = 1;    let b = a;   (直接复制值 1，互不相干)
  o1 ──[0x9F01]──┐
                 ├──► 共指同一块堆对象 { n: 1 }  (改 o2.n，o1.n 同步变化)
  o2 ──[0x9F01]──┘
```

1. **七大基本类型 vs 引用对象**：基本类型共 7 个（`string`、`number`、`boolean`、`null`、`undefined`、`symbol`、`bigint`），按值存放、按值判等；其余一切（对象、数组、函数、Map/Set）皆为引用类型，按内存地址判等（`{} === {}` 为 `false`）。
2. **传参一律按值，但「地址本身也是值」**：JS 函数传参没有 C++ 那种引用传递。传对象进函数时，拷贝的是地址值：在函数里 `obj.x = 2` 是拿钥匙开柜子改内容（外面看得到）；在函数里 `obj = { x: 2 }` 是把自己的钥匙扔了换把新钥匙（外面原对象纹丝不动）。
3. **三大经典边界坑**：① `typeof null === 'object'` 是初代引擎用全零低位标类型留下的历史 bug；② `'abc'.toUpperCase()` 能调方法是因为引擎瞬间做了**临时包装类装箱**，执行完立刻销毁；③ `Object.is` 修补了 `===` 的两个漏洞（`Object.is(NaN, NaN)` 为 `true`，`Object.is(+0, -0)` 为 `false`），React 的 `useState` 底层正是用 `Object.is` 判等。

**考场口述**：

「基本类型和引用类型的核心差异在**存储方式与赋值语义**。7 种基本类型直接按值存放和比较，赋值就是完整复制一份副本；而引用类型的数据本体在堆内存，变量里存的只是内存地址，赋值和传参复制的都是这把地址钥匙，所以多个变量修改属性会互相影响，但给形参重新赋一个新对象不会影响外部实参。面试里常连带考三个细节：一是 `typeof null` 返回 `'object'` 属于历史机器码标记 bug；二是基本类型调方法靠的是引擎临时装箱；三是 React 状态更新对比用的是 `Object.is` 而不是 `===`，因为它能正确处理 `NaN` 相等和正负零区分。」

### 10.`==` 和 `===` 的区别

**记忆锚点**：**全等直比不废话，双等暗转成数字；全站一律用 `===`，唯独判空留 `== null`**。

**痛点与直觉**：

JS 当年为了让网页脚本「怎么写都不报错」，给 `==` 塞了一套九曲十八弯的**隐式类型转换流水线**，结果造出了 `[] == false` 为真、`[] == ![]` 也为真的魔幻现象。在严谨的工程和 TS 项目里，我们绝不让运行时替我们猜类型。

**核心机制**：

```
x == y 隐式转换漏斗：
  ├─ 1. 两边同为 null / undefined ──► 直接 true（且它们与其它任何值比均为 false，故 null == 0 为 false）
  ├─ 2. 对象 vs 基本类型 ───────────► 对象调 valueOf() -> toString() 拆成基本类型（[] -> ""）
  └─ 3. 字符串/布尔 vs 数字 ────────► 统统强转成 Number 再比（"" -> 0，false -> 0，故 [] == false 为 true）
```

1. **`===` 的铁律**：先比类型，类型不同直接 `false`，绝不触发任何隐式转换；引用类型直接比内存地址。
2. **`==` 怪题一眼拆解法**：碰到 `[] == false`，左边数组先 `toString()` 变空串 `""`，再跟右边 `false` 一起转数字变成 `0 == 0`，所以为 `true`；而 `null == 0` 因为规范规定 `null / undefined` 不转数字，所以直接为 `false`。
3. **工程里唯一合法的 `==`**：写 `if (x == null)`，一句话同时拦截 `null` 和 `undefined`，既简洁又不会误伤 `0` 和 `""`，ESLint 的 `eqeqeq: ["error", "smart"]` 专门为它留了绿灯。

**考场口述**：

「`===` 是严格相等，要求类型和值都相同，不做任何转换；`==` 是宽松相等，类型不同时会触发隐式转换，核心方向是先把对象通过 `valueOf` 和 `toString` 拆成基本类型，再把布尔和字符串统一转成数字来比，唯独 `null` 和 `undefined` 互通且不转数字。在实际工程中我们配合 ESLint 全面禁用 `==`，只有一个场景例外：就是用 `x == null` 同时判断 `null` 和 `undefined`。」

### 11.深浅拷贝的实现和坑

**记忆锚点**：**浅拷只剥第一层皮，JSON 深拷丢函数断循环，现代首选 `structuredClone`**。

**痛点与直觉**：

在 React 或状态管理里，直接改原对象会导致引用地址不变、组件不重渲染。如果你用 `{ ...obj }` 或 `Object.assign` 拷一层，表面看是个新壳子，但里面的嵌套数组还是原来那把钥匙（**浅拷贝：换皮不换瓤**）。要想彻底斩断所有层级的藕断丝连，就得把里里外外所有嵌套容器全部换新（**深拷贝**）。

**核心机制**：

```
【浅拷贝 {...obj}】      新壳 ──► 内部子对象仍指回原堆地址 (改 a.child.x，原对象跟着变)
【深拷贝三路线对比】
  ├─ 1. JSON.parse(JSON.stringify(x)) ──► 快但残废：丢 undefined/函数/Symbol，Date 变字符串，循环引用直接崩
  ├─ 2. structuredClone(x) (现代内置) ──► 原生支持 Map/Set/Date/RegExp/循环引用，仅不支持函数与原型链
  └─ 3. 手写递归 + WeakMap            ──► WeakMap 记已拷贝对象破循环引用，Reflect.ownKeys 保留 Symbol
```

1. **JSON 往返法的「七宗罪」**：丢 `undefined`、丢函数、丢 `Symbol`、`Date` 变成字符串、`Map / Set / RegExp` 变成空 `{}`、`NaN / Infinity` 变成 `null`、遇到循环引用或 `bigint` 直接抛异常。
2. **原生 `structuredClone` 是现代首选**：浏览器和 Node 17+ 原生内置，底层走结构化克隆算法，完美处理循环引用、`Map / Set`、`Date`、`ArrayBuffer`；唯一限制是不能拷函数、DOM 节点和类原型链。
3. **手写深拷贝必答 `WeakMap`**：面试官让你手写深拷贝，考的不是 `for...in`，而是**用 `WeakMap` 记录「原对象 → 新副本」防止 `a.self = a` 栈溢出**，以及用弱引用保证拷贝完自动释放内存。

**考场口述**：

「浅拷贝像展开运算符和 `Object.assign`，只复制对象的第一层属性，嵌套的子对象依然共享内存地址；深拷贝则是递归创建所有层级的独立副本。实现深拷贝主要有三种方案：早期常用的 `JSON.stringify` 再 `parse` 缺陷很多，会丢失函数、`undefined`、`Symbol`，把 `Date` 变字符串，遇到循环引用直接报错；现代浏览器和 Node 环境首选原生内置的 **`structuredClone`**，它原生支持循环引用、`Map`、`Set` 和 `Date`；如果需要连原型链或特殊结构一起定制深拷贝，手写递归时核心是用 **`WeakMap` 缓存已拷贝过的对象引用**来解决循环引用导致的爆栈问题。」

### 12.🌟`any`、`unknown`、`never` 分别什么时候用

**记忆锚点**：**`any` 拆掉安检门，`unknown` 锁进保险箱（万物可进、开箱才出），`never` 是空集兜底（万物不进、可赋万物）**。

**痛点与直觉**：

死背表格最容易把 `unknown` 和 `never` 的赋值方向记反。只要记住「**集合大小与大楼安检**」的画面，一辈子不会混：
- **`unknown` 是全集（大楼门口的透明保险箱）**：全天下任何东西都能塞进这个箱子（任何类型都可赋给 `unknown`）；但在你做安检开箱（类型收窄）证明它是什么之前，绝对不准把它拿出来直接调属性，也不准随便塞给 `string` 变量。
- **`never` 是空集（绝对真空）**：里面连空气都没有，所以没有任何值能塞进 `never`；但数学上**空集是任何集合的子集**，所以 `never` 可以合法赋给任何类型，用来做分支穷尽检查的最后一块拼图。
- **`any` 是拆掉安检门**：既能随便进，又能随便出，还会像病毒一样把整条调用链全部传染成无类型状态。

**核心机制**：

```
        【顶类型 Top Type：unknown】  ◄── 万物皆可赋给它；但未收窄前，不可赋给具体类型、不可读属性
             ╱        │        ╲
       string       number     User  （中层具体类型）
             ╲        │        ╱
       【底类型 Bottom Type：never】  ──► 无物可赋给它（除非也是 never）；但它可赋给任何类型
   ---------------------------------------------------------------------------------
   【法外狂徒：any】 双向打通（关闭类型检查，顺着 a.b.c 向下游传染）
```

1. **外部入口一律接 `unknown`**：`JSON.parse` 返回值、`try...catch(e)` 的异常对象、第三方 postMessage 消息，全部标 `unknown`，逼着下游先写 `typeof`、类型守卫或 zod 校验才能消费。
2. **分支出口一律兜 `never`**：在 `switch (x.kind)` 的 `default` 分支写 `const _exhaustive: never = x`；一旦将来联合类型加了新成员而忘了补 `case`，`x` 无法缩成空集 `never`，编译期立刻标红报警。
3. **秒分 `void` 与 `never`**：`void` 是「函数正常跑到底、平安回来了，只是两手空空没带礼物（返回 `undefined`）」；`never` 是「函数半路抛异常炸了或掉进死循环，控制流永远回不来」。

**考场口述**：

「这三者我是按集合论里的**顶类型和底类型**来记的。`unknown` 是安全的顶类型，代表全集，就像带锁的保险箱，任何值都能赋给它，但在做类型收窄之前不能读属性也不能赋给具体类型，工程里专门用来接 `JSON.parse` 和 `catch` 的外部未知输入；`never` 是底类型，代表空集，没有任何值能赋给它，但它作为空集可以赋给任何类型，除了标永不返回的函数，最核心的用法是在 `switch default` 里做**编译期穷尽检查**；而 `any` 是直接关掉检查器并向下游传染，除了历史代码迁移平时严禁使用。」

### 13.🌟类型收窄有哪几种手段

**记忆锚点**：**控制流过三道筛：原语查 `typeof`、对象看标签（判别联合/`instanceof`/`in`）、复杂逻辑写谓词（`is` / `asserts`）**。

**痛点与直觉**：

你手里拿到一个 `string | number` 或 `Success | Fail` 的联合类型，或者一个锁在 `unknown` 保险箱里的包裹，编译器只允许你调它们共有的属性。要想调用专属方法，你必须在运行时写一段判断逻辑，同时让编译器看懂：「**走过这道安检门，留下的必然是某种具体类型**」——这个「运行时判断与编译期推导同步收缩」的过程就是类型收窄（Narrowing）。

**核心机制**：

```
联合类型 / unknown
  ├─ 第 1 筛：基础原语与空值 ──► typeof x === 'string'  |  x != null (同时筛掉 null 和 undefined)
  ├─ 第 2 筛：对象结构与标签 ──► r.ok === true (判别联合，最稳)  |  x instanceof Error  |  'id' in x
  └─ 第 3 筛：自定义函数承诺 ──► function isUser(x): x is User   |  function assert(x): asserts x is User
```

1. **对象联合首选「可辨识联合（Discriminated Unions）」**：给每个分支加一个共同的字面量标签字段（如 `kind: 'circle' | 'square'` 或 `ok: true | false`），比用 `'radius' in x` 更稳，且不会误查原型链。
2. **自定义类型谓词 `x is T` 是人为担保**：当判断逻辑抽成独立函数时，返回 `boolean` 会丢失收窄信息，必须把返回类型写成 `x is User`；注意编译器信了你的签名而不验函数体，里面判断一定要写严。
3. **跨异步回调收窄会失效**：如果先 `if (x !== null)`，再在 `setTimeout(() => x.trim())` 里用 `x`，编译器会报错——因为异步执行时外层变量 `x` 可能被改成 `null` 了。解法是用 `const s = x` 把收窄后的快照锁进常量。

**考场口述**：

「类型收窄就是通过运行时的条件分支，让 TS 控制流分析器把宽泛的联合类型或 `unknown` 缩小为具体类型。我平时把它归为三类手段：第一类针对**基本类型和空值**，用 `typeof` 和 `x != null`；第二类针对**对象联合**，工程上最推荐带字面量标签的**判别联合**，其次是 `instanceof`、`Array.isArray` 和 `in` 操作符；第三类针对**抽离出来的校验函数**，必须显式标注类型谓词 `x is T` 或断言函数 `asserts x is T`。另外要注意，收窄状态跨异步回调会失效，需要先赋给 `const` 局部变量把类型锁住。」

### 14.字面量类型和 `as const`

**记忆锚点**：**默认推断爱放宽（`'a'` 变 `string`），`as const` 一锤锁死「最窄字面量 + 全层 readonly」**。

**痛点与直觉**：

当你写 `const req = { method: 'GET' }` 时，TS 默认猜你以后可能会改 `req.method = 'POST'`，于是好心把 `method` 的类型放宽（Type Widening）成了 `string`。结果你把 `req` 传给要求 `method: 'GET' | 'POST'` 的函数时，编译器反手给你报了个错：`string` 不能赋给 `'GET' | 'POST'`！这时候你就需要 `as const` 告诉编译器：「**别替我放宽，按最死、最窄的字面量给我焊死！**」

**核心机制**：

```
const a = { kind: 'circle', pos: [10, 20] };
  └─ 默认拓宽 ──► { kind: string; pos: number[] }          (丢了字面量 'circle'，丢了元组长度 2)

const b = { kind: 'circle', pos: [10, 20] } as const;
  └─ 常量断言 ──► { readonly kind: 'circle'; readonly pos: readonly [10, 20] } (最窄字面量 + 递归只读)
```

1. **一锤干两件事（锁窄 + 深只读）**：不仅把字符串/数字锁死成具体字面量类型，还把对象所有嵌套层级加上 `readonly`，把数组直接锁成定长只读元组 `readonly [10, 20]`。
2. **与 `: readonly` 修饰符的差异**：类型声明里的 `readonly` 只管「不准改引用」且只管浅层第 1 层；`as const` 是值层面的断言，既递归加只读，又阻止字面量拓宽。
3. **只锁编译期，不冻运行时**：`as const` 编译后直接擦除，不会生成 `Object.freeze()`；如果需要在运行时也禁止篡改，还得显式调 `Object.freeze`。

**考场口述**：

「TS 对对象属性和数组默认有**类型拓宽机制**，比如对象里的 `'GET'` 会被自动放宽成 `string`，导致判别联合或字面量参数匹配失败。加上 `as const` 常量断言后，编译器会同时做两件事：一是关闭拓宽，把所有值锁定为**最窄的字面量类型**；二是给对象的每一层属性和数组都加上**深度 `readonly`**，把普通数组变成定长只读元组。工程里常用来定义路由表、Redux action、以及替代 `enum` 枚举。」

### 15.`satisfies` 解决什么问题

**记忆锚点**：**`: Type` 验了格式丢了细节，`as Type` 强行指鹿为马，`satisfies` 既验格式又保原貌**。

**痛点与直觉**：

在 TS 4.9 之前，写配置对象永远面临一个「**保大还是保小**」的死局：
- 如果你写 `const routes: Record<string, string> = { home: '/' }`（**保格式校验**），编译器帮你验了值都是字符串，但 `routes.home` 的具体键和 `'/'` 字面量被大帽子抹平了，连自动补全都没了；
- 如果你不写类型标注（**保具体字面量**），`routes.home` 保住了，但同事手滑写了个 `port: 80` 混进去，编译器却不报错。

`satisfies` 就是破局者：**它只拿着模具过来比划一下合不合格，比划完立刻拿走，绝不覆盖变量原本精确的推断类型**。

**核心机制**：

```
方式                格式校验？   保留具体键与字面量？   安全性
-------------------------------------------------------------------------
const x: Type = v      ✓ 校验       ✗ 被拓宽成宽泛 Type    安全但丢失细节
const x = v as Type    ✗ 盲信       ✗ 强行改写成 Type      极危险（指鹿为马）
const x = v satisfies  ✓ 校验       ✓ 完整保留原推断类型   鱼与熊掌兼得
```

1. **只验不改（检验与推断解耦）**：`expr satisfies Type` 要求 `expr` 必须能赋给 `Type`，验证通过后，变量依然保留 `expr` 自身最精确的子类型。
2. **彻底吊打 `as` 断言**：`as` 是欺骗编译器跳过检查，而 `satisfies` 是严格执行编译检查，写错属性当场标红。
3. **黄金搭档 `as const satisfies Type`**：先用 `as const` 锁死字面量和只读元组，紧接着用 `satisfies` 校验整体结构符合契约，是现代 TS 写配置表、主题色板、路由表的终极范式。

**考场口述**：

「`satisfies` 是 TS 4.9 引入的操作符，专门解决**类型校验与精确类型推断不可兼得**的痛点。以前我们给配置对象加 `: Record<string, string>` 类型标注，虽然能校验属性格式，但会把对象具体的键名和字面量类型拓宽抹平，导致下游失去精确的自动补全。用 `satisfies` 则只做兼容性校验、不改变变量原本的推断类型，实现了**既校验外层契约、又保留内层最窄类型**，工程上常和 `as const` 组合使用。」

### 16.`null` 和 `undefined` 在严格模式下

**记忆锚点**：**非严格空值当内鬼，严格模式单列门户；链式访问用 `?.`，兜底默认用 `??` 忌 `||`**。

**痛点与直觉**：

汤姆·霍尔曾把 `null` 称为「十亿美元的错误」。在 TS 关闭严格模式时，`null` 和 `undefined` 就像幽灵一样是所有类型的子类型——一个标着 `string` 的变量里随时可能躺着 `null`，调 `.trim()` 当场炸穿线上。打开 `strictNullChecks` 后，TS 把这两个幽灵从所有类型里踢出来单独关押：你不显式写出 `string | null`，谁也别想往里塞空值。

**核心机制**：

```
strictNullChecks: false ──► string 集合内部暗藏 null / undefined（随时引爆空指针）
strictNullChecks: true  ──► string 与 null / undefined 彻底隔离，必须显式联合並收窄后使用
```

1. **`??`（空值合并）与 `||`（逻辑或）的生死界限**：`a || 10` 把所有假值（含合法的 `0`、`""`、`false`）全当空处理，分页传 `page = 0` 或输入框为空串时直接出 bug；`a ?? 10` **只在 `a` 为 `null` 或 `undefined` 时才走默认值**。
2. **可选属性 `a?: string` vs `a: string | undefined`**：默认情况下 `a?: string` 等价于允许不传或传 `undefined`；一旦开启 `exactOptionalPropertyTypes`，`a?: string` 只允许「省略该键」，不允许显式传 `{ a: undefined }`。
3. **慎用非空断言 `x!.prop`**：感叹号 `!` 只是编译期消音器，没有任何运行时保护；除非紧跟在 `map.has(k)` 之后调 `map.get(k)!`，否则一律用 `?.` 可选链或守卫分支代替。

**考场口述**：

「在关闭 `strictNullChecks` 时，`null` 和 `undefined` 可以赋给任意类型，等于放弃了空指针防御；开启后它们变成独立类型，必须显式写进联合类型并通过收窄才能访问属性。日常处理空值有三个要点：第一，给默认值一定要用 **`??` 空值合并**而不是 `||`，防止把合法的数字 `0` 和空字符串误判为空；第二，深层属性读取用 `?.` 可选链短路；第三，严禁滥用 `!` 非空断言掩盖潜在的空值风险。」

### 17.🌟`type` 和 `interface` 怎么选

**记忆锚点**：**`interface` 造积木（可同名拼接、专职对象），`type` 写算式（可联合映射、通吃万物）**。

**痛点与直觉**：

这题几乎是 TS 面试出现频率第一名，但只答「一个能合并一个不能」太单薄。从编译器视角看，两者的设计初衷完全不同：
- **`interface` 是「定义一张面向对象的蓝图」**：它只关心对象、类和函数长什么形状，并且天生支持「打补丁」（同名接口自动合并），方便你给第三方库或 `Window` 追加属性。
- **`type` 是「给任意类型表达式起外号」**：它是类型层面的变量赋值（`type X = ...`），右边不仅能放对象，还能放基本类型、联合（`|`）、元组、条件运算（`extends ? :`）和映射遍历（`in keyof`）。

**核心机制**：

```
                   ┌─ 同名自动合并 (Declaration Merging) ──► 仅 interface 支持（给 Window/三方库打补丁）
对象 / 类 / 函数 ──┤
                   └─ 联合 (A|B) / 元组 / 映射 / 条件计算 ──► 仅 type 支持（类型体操与组合运算）
```

1. **核心差异一：同名声明合并**：两个同名 `interface Window` 会自动拼成一个；两个同名 `type` 直接报重复标识符错。因此扩展全局类型或第三方库（如给 `express.Request` 挂 `user`）**只能用 `interface`**。
2. **核心差异二：表达能力边界**：`interface` 的右边必须是一个确定的对象块 `{ ... }`；而 `type` 右边可以是基础类型别名、联合类型 `A | B`、`typeof obj`、映射类型 `[K in keyof T]`，遇到联合或类型运算**只能用 `type`**。
3. **核心差异三：编译器缓存与报错体验**：`interface extends` 在编译器内部有按名称缓存的快速通道，报错时直接报接口名；`type` 的 `&` 交叉类型在深层嵌套时会递归展开所有成员，大型项目里对象继承优先用 `interface extends` 编译更快。

**考场口述**：

「`interface` 和 `type` 在描述普通对象和函数时可以互换，但底层定位不同：**`interface` 是声明对象契约，而 `type` 是给任意类型表达式起别名**。具体有三个核心差异：第一是**声明合并**，同名 `interface` 会自动合并属性，适合给 `Window` 或第三方库打补丁，`type` 则不支持；第二是**表达范围**，联合类型、元组、映射类型和条件类型只能用 `type` 表达；第三是**编译性能**，`interface extends` 会被编译器按名字缓存，比 `type` 的 `&` 交叉运算在大型项目里检查更快。我们团队的规范是：定义对象结构和类契约优先用 `interface`，做联合、提取和类型运算一律用 `type`。」

### 18.🌟什么是结构类型

**记忆锚点**：**Java 查户口本（名义类型），TS 玩鸭子测试（结构类型）——长得像就能塞，防串号靠品牌标签（Branded Type）**。

**痛点与直觉**：

在 Java 里，哪怕两个类字段一模一样，只要没写 `implements Point`，编译器就死活不认它们是一家（**名义类型：看血统户口**）。但 JS 世界里到处是随手写的匿名对象字面量 `{ x: 1, y: 2 }`，如果非要挨个声明继承关系，前端就没法写了。所以 TS 采用**结构类型（鸭子类型）**：只要一个东西走起来像鸭子、叫起来像鸭子（具备目标要求的全部属性），哪怕它没办户口，也直接放行！

**核心机制**：

```
【结构兼容（多退少补）】
  目标类型 Point { x: number; y: number }
  源变量   vec = { x: 1, y: 2, z: 3 }  ──► 属性只多不少，赋值 p = vec 直接通过！
  （例外：直接传新鲜字面量 { x: 1, y: 2, z: 3 } 会触发「多余属性检查」防手滑拼错）

【语义防串号：品牌类型 Branded Type】
  type UserId  = string & { readonly __brand: 'UserId' };
  type OrderId = string & { readonly __brand: 'OrderId' };  ──► 形状不同，彻底杜绝把订单号传给用户 ID！
```

1. **对象兼容看「属性多退少补」，函数兼容看「参数少退多补」**：对象赋值时，源对象属性比目标多没关系（只要包含目标要求的全部属性即可）；函数赋值时，实现函数的参数比目标签名少也没关系（比如 `[1,2].map(x => x)` 忽略后面的 `(index, array)` 参数完全合法）。
2. **字面量多余属性检查（Excess Property Check）**：为什么 `const p: Point = { x: 1, y: 2, z: 3 }` 会报错，而先赋给变量 `const v = { x: 1, y: 2, z: 3 }; const p: Point = v` 就不报？因为编译器专门对**新鲜对象字面量**加了一道防手滑检查，防止你把可选属性拼错名字。
3. **如何模拟名义类型（Branded Types）**：结构类型的缺点是 `type UserId = string` 和 `type OrderId = string` 会随意互串。工程里通过交叉一个虚拟私有标签 `string & { readonly __brand: unique symbol }` 或利用类的 `#private` 私有字段，就能在结构系统里造出绝对不互串的名义类型。

**考场口述**：

「TS 采用的是**结构类型系统**，而 Java 采用的是名义类型系统。也就是说 TS 判断两个类型是否兼容，不看它们的名字或有没有显式 `implements`，只看**属性形状是否包含**。这带来了两个高频考点：一是对象赋值遵循属性只多不少，但直接传新鲜对象字面量会触发额外的**多余属性检查**来防拼写错误；二是结构类型容易导致同样底层的 `UserId` 和 `OrderId` 互相串用，工程上我们会通过交叉一个虚拟的 `__brand` 属性构造**品牌类型（Branded Types）**，来模拟名义类型的强隔离。」

### 19.类里的访问修饰符

**记忆锚点**：**`private` 是君子协定（编译后裸奔），`#field` 才是防盗铁门（V8 引擎级硬隔离）**。

**痛点与直觉**：

很多同学以为在类属性前写个 `private secret = 123` 就高枕无忧了。殊不知 TS 的 `private` 在编译成 JS 后会被擦得一干二净，变成普普通通的 `this.secret = 123`，别人 `console.log(instance['secret'])` 或 `JSON.stringify` 一眼就能看光。如果你需要连运行时都撬不开的真私有，必须用 ES2022 原生的井号私有字段 `#secret`。

**核心机制**：

```
修饰符         类内部   子类   外部实例   编译成 .js 后的真面目
--------------------------------------------------------------------------------
public          ✓       ✓       ✓        普通属性 this.x（默认）
protected       ✓       ✓       ✗        普通属性 this.x（擦除修饰符，运行时仍裸奔）
private         ✓       ✗       ✗        普通属性 this.x（擦除修饰符，obj['x'] 能偷看）
#field (ES原生) ✓       ✗       ✗        引擎级硬私有槽位（外部连 Reflect/JSON 都读不到）
```

1. **软私有 `private` vs 硬私有 `#field`**：`private` 只在编译期拦君子，运行时 `Object.keys`、`JSON.stringify`、`obj['x']` 全能穿透；`#field` 是 JS 语言规范原生的强私有，外部访问直接语法报错，连序列化都不会暴露。
2. **`readonly` 只管浅层第一道锁**：`readonly list: number[]` 只禁止 `this.list = []` 换引用，拦不住 `this.list.push(1)` 改内容；要连内容一起锁必须写成 `readonly list: readonly number[]`。
3. **构造函数参数属性语法糖**：`constructor(private readonly api: ApiService) {}` 一行顶三行——自动声明同名属性、加上修饰符、并在构造函数体内生成 `this.api = api` 赋值语句。

**考场口述**：

「TS 类里的访问修饰符除了常规的 `public`、`protected`、`private` 和 `readonly`，最核心的考点是 **`private` 与 ES 原生 `#` 私有字段的区别**。TS 的 `private` 属于编译期软约束，经过类型擦除后在产物里就是普通属性，运行时通过中括号索引或 `JSON.stringify` 依然能读到；而 `#field` 是 JS 引擎层面的硬私有，运行时彻底隔离。另外要注意 `readonly` 修饰符是浅层的，只锁引用不锁内部元素修改。」

### 20.抽象类和接口

**记忆锚点**：**接口是纯合同（只签字不干活、可多签、编译蒸发），抽象类是半成品车间（有公共底座、仅单继承、运行保留）**。

**痛点与直觉**：

什么时候写 `interface`，什么时候写 `abstract class`？看你需不需要「**塞公共代码和公共状态**」。如果只是规定「所有支付插件都得有 `pay()` 方法」，用纯合同 `interface` 最轻；如果十几个支付插件都有一套一模一样的「签名重试 + 日志打点」底子，只有最后一步发请求不同，那就建一个半成品车间 `abstract class BasePayment`，把公共活干完，留一个 `abstract doRequest()` 洞让子类填。

**核心机制**：

```
维度               interface 接口 (纯契约)         abstract class 抽象类 (半成品基类)
-----------------------------------------------------------------------------------
能否带方法实现      ✗ 只能写签名，0 实现             ✓ 既能写具体公共方法，也能留 abstract 空洞
能否存实例状态      ✗ 无运行时状态                   ✓ 可定义实例字段与 constructor 构造函数
继承/实现数量       ✓ 一个类可 implements 多个接口   ✗ 单继承，一个子类只能 extends 一个抽象类
编译后运行时产物    ✗ 彻底擦除，0 字节               ✓ 保留为真实的 JS class（可用于依赖注入 Token）
```

1. **`is-a` 复用基座用抽象类，`can-do` 能力契约用接口**：多个同类业务共享状态与模板方法（Template Method 模式）选 `abstract class`；跨物种横向赋予能力（如 `Disposable`、`Serializable`）选 `interface`。
2. **运行时存在性差异**：在 NestJS 等依赖注入框架里，因为 `interface` 编译后蒸发，不能直接当构造函数注入 Token，而 `abstract class` 编译后保留了真实类引用，既能当接口约束又能直接当注入 Token。
3. **抽象类不可直接 `new`**：编译器禁止 `new BaseRepo()`，必须由子类补齐所有 `abstract` 方法后才能实例化。

**考场口述**：

「接口和抽象类的本质区别在于**是否包含运行时实现与状态**。接口是纯粹的类型契约，不包含任何方法实现，一个类可以实现多个接口，且编译后接口会被完全擦除；而抽象类是『半成品基类』，既可以声明抽象方法让子类填空，也可以包含公共的方法实现、实例字段和构造函数，但只支持单继承且编译后会保留为真实的 JS 类。工程上，单纯约束数据结构或跨类能力用接口，需要复用公共逻辑底座或走模板方法模式时用抽象类。」

### 21.函数重载怎么写

**记忆锚点**：**上面写多份对外菜单（重载签名），底下配一个万能后厨（实现签名），运行时靠分支自己拆包**。

**痛点与直觉**：

Java 的函数重载是真有好几个同名方法，JVM 按参数类型分派；但 JS 里同名函数只会后者覆盖前者，根本没有运行时重载！为了表达「传字符串进来返回数字，传数字进来返回字符串」这种**入参类型与返回值类型一对一联动**的关系，TS 设计了「多头单身」的重载语法。

**核心机制**：

```ts
// 1. 对外菜单（重载签名）：调用方只能看到这两行，精确锁定「入参 → 返回值」映射
function format(x: string): string[];
function format(x: number): number;

// 2. 万能后厨（实现签名）：对外隐身！类型必须宽到能兜住上面所有菜单
function format(x: string | number): string[] | number {
  return typeof x === 'string' ? x.split(',') : x * 2;
}
```

1. **菜单与后厨分离规则**：上面的重载签名没有函数体，专门给调用方和 IDE 看；最下面的实现签名带函数体，**对外部调用者完全不可见**（如果上面只有 `(string)` 和 `(number)` 两个签名，外部传 `string | number` 反而会报错，除非实现签名也复制到上面）。
2. **什么时候用泛型条件类型代替重载**：如果只是参数数量固定、返回类型随入参变化，写 `<T extends string | number>(x: T): T extends string ? string[] : number` 往往比写三四行重载签名更紧凑；只有不同分支的参数个数、含义完全不同时（如 `createElement`），才必须用函数重载。
3. **隐藏技能：`this` 伪参数**：函数第一个参数可以写 `function onClick(this: HTMLButtonElement, e: Event)`，专门用来约束函数体内的 `this` 类型，编译后这个伪参数会自动抹掉，不占实际实参位置。

**考场口述**：

「TS 的函数重载和 Java 不同，它只在编译期生效，产物里最终只有一个 JS 函数。写法上分为两部分：上面写多个不带函数体的**重载签名**，用来给调用方建立精确的『入参到返回值』类型映射；最下面写一个带函数体的**实现签名**，它的参数和返回值必须兼容上面所有签名，且该签名对外部调用者不可见。因为擦除后运行时只有一个函数，函数体内部依然要自己用 `typeof` 或参数长度判断走哪个分支。」

## 泛型

### 22.🌟泛型解决什么问题

**记忆锚点**：**类型当成参数传，同套逻辑锁关联**——既不写死成单一类型，也不像 `any` 那样把出入参关系斩断。

**痛点与直觉**：

写一个返回数组首元素的函数 `first(arr)`：
- 如果写死 `number[] => number`，那传字符串数组就得再抄一遍代码（**丢了复用性**）；
- 如果写成 `any[] => any`，传入 `string[]` 拿出来的变成了 `any`，后面调什么都不报错（**斩断了输入与输出的因果锁链**）。

泛型 `<T>` 就是一台「**带记忆模子的自动售货机**」：你投进苹果（`T = Apple`），出口锁死吐苹果；你投进硬币（`T = Coin`），出口锁死吐硬币——机器只有一台，但进出货物的类型因果关系被死死锁住。

**核心机制**：

```
【用 any：锁链断裂】    input (string[]) ──► [ fn(x: any): any ] ──► output (any，类型丢失！)
【用泛型：因果锁死】    input (T[])      ──► [ fn<T>(x: T[]): T ] ──► output (T，传 string[] 必得 string)
```

1. **锁死多处位置的类型关联**：泛型最核心的价值不是「能接任意类型」（`unknown` 也能接），而是**把参数与返回值、或者多个参数之间的类型绑定在一起**，比如 `pair<T>(a: T, b: T): [T, T]` 强迫两个入参必须同型。
2. **四大栖息地与默认推断**：函数、接口、类、类型别名（`type`）都能带 `<T = DefaultType>`。绝大多数函数调用靠实参就能自动反推 `T`，只有当 `T` 仅出现在返回值里（如 `axios.get<User>(url)`）时才需要手动传 `<User>`。
3. **擦除边界**：泛型只在编译期跑，运行时没有 `T`，不能 `new T()`。

**考场口述**：

「泛型本质上是**类型层面的函数参数**，它解决的是『代码复用与类型安全不可兼得』的痛点。如果不用泛型，通用函数要么为每种类型重复写一遍，要么用 `any` 导致输入和输出之间的类型关联彻底断裂。引入泛型 `<T>` 后，编译器可以根据传入的实参自动推导出具体类型，并把参数与返回值、或者多个参数之间的类型关系锁死。工程里无论是封装通用请求函数 `request<T>`、React 组件 `Table<RecordType>` 还是写工具类型，都离不开泛型。」

### 23.泛型约束

**记忆锚点**：**裸 `<T>` 当成盲盒看，加 `extends` 划定底线，`<T, K extends keyof T>` 锁死对象取键**。

**痛点与直觉**：

裸写的 `<T>` 就像一个完全密封的盲盒——因为调用方可能塞个数字 `123` 进来，也可能塞个 `null` 进来，所以你在函数里写 `x.length` 编译器立刻翻脸报错：万一它没有 `length` 呢？要想在函数里合法访问属性，就必须用 `extends` 给盲盒划一道**最低准入门槛**：`<T extends { length: number }>`，意思是「凡是进我这扇门的 `T`，身上至少得带着 `length` 属性」。

**核心机制**：

```ts
// 黄金范式：两个泛型参数互相约束，锁死「对象 + 合法属性名 → 精确属性值类型」
function pluck<T extends object, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

const users = [{ id: 1, name: 'Alice' }];
const names = pluck(users, 'name');   // 自动推导出 string[]
pluck(users, 'notExist');             // 编译期直接报错拦截！
```

1. **单参数划底线（`T extends Base`）**：限定 `T` 必须包含某些字段（如 `T extends { id: string }`）或属于某个联合子集（如 `T extends string | number`），函数体内即可安全读取对应成员。
2. **双参数联动锁键（`K extends keyof T`）**：这是 TS 面试手写率第一的模板，第一个参数接对象 `T`，第二个参数用 `keyof T` 把键名 `K` 锁死在 `T` 已有的属性里，返回值用索引访问类型 `T[K]` 精准拿到该属性的值类型。
3. **声明顺序左先右后**：被依赖的类型参数写在前面（`<T, K extends keyof T>`），虽然 TS 允许交叉引用，但按依赖顺序排列最清晰且方便给定默认值。

**考场口述**：

「不加约束的泛型 `<T>` 在函数内部等同于 `unknown`，任何属性都不能直接访问。泛型约束就是用 **`T extends 某类型`** 给类型参数划定最小结构边界。工程里最经典的模式是双泛型联动 **`<T extends object, K extends keyof T>`**：用 `K extends keyof T` 保证传入的属性名一定存在于对象 `T` 上，再用索引类型 `T[K]` 作为返回值类型，从而在编译期彻底杜绝拼错属性名的问题。」

### 24.协变、逆变、双变

**记忆锚点**：**产出返回值是协变（子替父），吞入参数是逆变（父替子），TS 方法签名留了双变后门**。

**痛点与直觉**：

为什么 `Dog` 是 `Animal` 的子类，但 `(d: Dog) => void` 却**不能**赋给 `(a: Animal) => void`，反而要把方向倒过来？

用「**招厨师（函数赋值）**」的直觉一秒想通：
- 老板贴告示要招一个「**专门处理狗（`(d: Dog) => void`）的驯兽师**」，意思是老板上场时只会牵一只真真切切的 `Dog`（既有 `.name` 又有 `.bark()`）交给你。
- 这时来了一个「**啥动物都能管的大师 `(a: Animal) => void`**」，他干活只看动物的名字 `.name`，根本不要求对方会叫——老板牵只狗给他，他完全能胜任！所以 **`(Animal) => void` 可以安全赋给 `(Dog) => void`（父替子，方向反转，叫参数逆变）**。
- 反过来，如果老板要招「管所有动物的人 `(a: Animal) => void`」，你却派去一个「非要让对方汪汪叫 `.bark()` 的狗专员 `(d: Dog) => void`」，老板牵只猫进去当场就炸了！

**核心机制**：

```
已知继承关系：Dog ⊆ Animal（Dog 属性更多、范围更窄，是子类型）

1. 【返回值位置：协变 Covariant（方向相同）】
   (() => Dog)  ───可安全赋给──►  (() => Animal)   （调用方只想要个动物，你给只狗完全满足）

2. 【函数参数位置：逆变 Contravariant（方向反转，需开启 strictFunctionTypes）】
   ((a: Animal) => void)  ───可安全赋给──►  ((d: Dog) => void)
   （调用方保证传入 Dog，实现方只读取 Animal 的公共属性，绝对安全！）
```

1. **口诀「出协入逆」**：凡是往外产出数据的位置（函数返回值、`Promise<T>`、只读数组 `readonly T[]`）都是**协变**（子类型可赋给父类型）；凡是往里接收消费数据的位置（函数参数）都是**逆变**（父类型参数函数可赋给子类型参数函数）。
2. **`strictFunctionTypes` 的双变妥协**：为了不让 `Array<Dog>` 赋给 `Array<Animal>` 报错，TS 对 `interface` 里的**方法语法 `method(x: T): void`** 留了后门，默认采用不安全的**双变（Bivariant）**；只有写成函数属性语法 `prop: (x: T) => void` 且开启 `strictFunctionTypes` 时，才严格执行参数逆变。
3. **利用函数参数逆变实现 `UnionToIntersection`（类型体操压轴技）**：把联合类型放到函数参数位置 `(x: U) => void`，再用 `infer` 推断参数，TS 就会因为参数逆变自动把联合类型 `A | B` 聚合成交叉类型 `A & B`。

**考场口述**：

「协变和逆变描述的是复合类型与子类型之间的赋值方向关系。核心规律是『**返回值协变，参数逆变**』。假设 `Dog` 是 `Animal` 的子类型：在返回值位置，返回 `Dog` 的函数可以安全赋给要求返回 `Animal` 的类型，方向一致叫协变；而在参数位置恰恰相反，接收 `Animal` 的函数才能安全赋给要求接收 `Dog` 的函数类型，因为调用方只会传入 `Dog`，而实现方只访问 `Animal` 的基础属性不会越界，方向反转叫逆变。另外在 TS 里，只有开启 `strictFunctionTypes` 且使用箭头函数属性写法时才会严格检查参数逆变，普通方法签名为了兼容数组协变依然保留了双变。」

## 高级类型

### 25.`keyof` 和 `typeof`

**记忆锚点**：**`typeof` 搭桥从「值」跨到「类型」，`keyof` 抽骨把「对象类型」拆成「键名联合」**。

**痛点与直觉**：

工程里最烦的是「改一处常量，要同步改两处类型定义」。要是能直接指着写好的 JS 常量对象说：「**编译器，照着这个活生生的对象，把它的类型给我拓印下来，再把所有键名抽出来当联合类型！**」——这就是 `keyof typeof obj` 黄金组合干的事：以值为本，类型自动跟着实现走。

**核心机制**：

```
【运行时值世界 (Value Space)】          【编译期类型世界 (Type Space)】
  const conf = { host: 'a', port: 80 } as const;
        │
        └──── 1. typeof conf (跨界拓印) ────► type Conf = { readonly host: 'a'; readonly port: 80 }
                                                    │
                                                    └──── 2. keyof Conf (抽键联合) ────► "host" | "port"
```

1. **黄金公式 `keyof typeof obj`**：`typeof` 在类型位置把 JS 变量转成 TS 类型，`keyof` 紧接着把该类型的所有公开属性名提取为字符串字面量联合。
2. **提取对象值类型的公式 `(typeof obj)[keyof typeof obj]`**：如果配了 `as const`，用这个公式就能直接把对象所有属性的**值**提取成字面量联合，完美替代 `enum`。
3. **两个边界细节**：`keyof any` 的结果永远是 `string | number | symbol`（JS 允许做对象键的三种原语）；如果对象带宽泛索引签名 `{ [k: string]: any }`，`keyof` 会因为数字键可自动转字符串而返回 `string | number`。

**考场口述**：

「`typeof` 和 `keyof` 是打通值空间与类型空间的两座桥梁。当 `typeof` 用在类型位置时，它可以把一个运行时 JS 常量或函数的静态类型提取出来；而 `keyof` 则作用于对象类型，把它的所有属性名提取成字面量联合类型。工程里最常用的是 **`keyof typeof obj`** 组合，配合 `as const` 可以直接从一份运行时配置常量里自动推导出键名联合与值联合，做到『只改一处常量，类型自动同步』。」

### 26.映射类型

**记忆锚点**：**`[K in keyof T]` 是类型层面的 `for...in` 循环，配 `+/-` 改修饰符，配 `as` 改键名或过滤**。

**痛点与直觉**：

假设 `User` 有 20 个必填字段，现在写编辑接口需要把这 20 个字段全变成可选的——总不能手抄一遍加 20 个问号吧？映射类型就是**类型世界里的批量流水线（`Array.map`）**：把原类型的键挨个拎出来过一遍模具，一键批量加上或撕掉 `?` 和 `readonly`。

**核心机制**：

```ts
// 映射类型四要素：[ 修饰符  K in 键集合  as 重映射键名 ] 修饰符 : 值类型
type Getters<T> = {
  -readonly [K in keyof T as T[K] extends Function ? never : `get${Capitalize<string & K>}`]-?: () => T[K];
};
// 1. -readonly / -? ：撕掉只读与可选修饰符（默认 + 号可省略）
// 2. K in keyof T   ：逐个遍历原类型的键（同态映射，自动保留原修饰符）
// 3. as ...         ：TS 4.1 键重映射；若算出 never 则直接滤掉该属性！
```

1. **加减修饰符（`+? / -?` 与 `+readonly / -readonly`）**：`Partial` 就是加 `?`，`Required` 就是用 `-?` 把问号撕掉，`Mutable` 就是用 `-readonly` 把只读锁拆掉。
2. **同态映射（Homomorphic）**：只要直接写 `in keyof T`，编译器就知道你是在改造原对象，会自动保留原属性的只读/可选状态，且传入数组或元组时还会保持数组/元组形态不会退化成普通对象。
3. **`as` 子句重映射与过滤**：在 `K in keyof T` 后面接 `as NewKey`，既能用模板字符串批量把 `name` 改名成 `getName`，又能通过返回 `never` 把不需要的属性直接剔除。

**考场口述**：

「映射类型就是类型层面的循环遍历，核心语法是 **`[K in keyof T]: T[K]`**，内置的 `Partial`、`Required`、`Readonly`、`Pick` 全是用它写的。掌握它只需要记三个抓手：第一是用 **`+` 和 `-` 控制修饰符**，比如 `-?` 可以去掉可选属性实现 `Required`；第二是**同态特性**，直接遍历 `keyof T` 会自动继承原属性的修饰符并保留元组结构；第三是 TS 4.1 引入的 **`as` 键重映射**，既能配合模板字面量批量改键名，也能通过返回 `never` 按值类型过滤属性。」

### 27.条件类型与分布式

**记忆锚点**：**`T extends U ? X : Y` 是类型三元表达式；裸泛型遇联合自动拆包分发，套方括号 `[T]` 一秒关分发**。

**痛点与直觉**：

条件类型就是类型层面的 `if...else`。但很多人在手写工具类型时会撞上一个怪事：传入 `'a' | 1`，怎么结果不是一个整体判断，而是自动拆成了两次判断再拼起来？

这就是**分布式条件类型（Distributive Conditional Types）**：当 `extends` 左边的 `T` 是个**光着身子的裸泛型参数**，且传进来的是联合类型 `A | B` 时，TS 会像乘法分配律一样自动拆包：`F<A | B> = F<A> | F<B>`。

**核心机制**：

```
【触发分发（裸类型参数 T）】
  type ToArray<T> = T extends any ? T[] : never;
  ToArray<string | number>  ──拆包分发──►  ToArray<string> | ToArray<number>  ──►  string[] | number[]

【阻止分发（用元组 [] 包一层脱掉「裸」身份）】
  type ToArrayNonDist<T> = [T] extends [any] ? T[] : never;
  ToArrayNonDist<string | number>  ──整体判断──►  (string | number)[]
```

1. **触发分发的两个铁条件**：① `T` 必须是泛型参数（直接写具体类型不分发）；② `T` 在 `extends` 左边必须是**裸露的**（不能包在 `T[]`、`Promise<T>` 或 `[T]` 里）。
2. **借分发筛除联合项（`Exclude` 与 `Extract` 原理）**：因为联合会被逐项拆开比对，只要把不想要的分支返回空集 `never`，合起来时 `never` 自动消失，就实现了联合类型的精准过滤。
3. **空集特例与如何判断 `IsNever<T>`**：因为 `never` 是空联合（0 个成员），裸泛型 `T` 传入 `never` 时连循环体都不进，直接返回 `never`！所以判断一个类型是不是 `never`，**必须套方括号关掉分发**：`type IsNever<T> = [T] extends [never] ? true : false`。

**考场口述**：

「条件类型用 `T extends U ? X : Y` 在编译期做分支判断，它最核心的机制是**分布式特性**：当 `extends` 左侧是未经过任何包装的**裸泛型参数**，并且传入的是联合类型时，编译器会自动把联合类型的每个成员拆开单独代入计算，最后再把结果联合成新类型，内置的 `Exclude` 和 `Extract` 就是靠把不匹配的成员映射成 `never` 实现过滤的。如果想关闭自动分发——比如实现 `IsNever<T>` 判断空集时——只需要给两边套上一层元组方括号写成 **`[T] extends [never]`** 即可。」

### 28.`infer`

**记忆锚点**：**条件分支里摆个捕兽夹 `infer U`，结构一对上，自动把目标位置内部的类型生擒出来**。

**痛点与直觉**：

条件类型 `T extends Promise<any>` 只能判断「它是不是个 Promise 盒子」，但如果你要把盒子**里面的东西**掏出来当返回值呢？你不能在左边凭空用未声明的变量，所以 TS 提供了 `infer U`——它就像在结构模具的指定槽位放了一个「**类型捕兽夹**」：只要传入的 `T` 能严丝合缝卡进外部模具，夹子所在位置的内部类型就会被自动捕获并命名为 `U`。

**核心机制**：

```ts
// 1. 扒函数返回值壳：夹子放在 => 右边
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;

// 2. 扒数组元素壳：夹子放在 [] 前面
type ElementOf<A>    = A extends readonly (infer E)[] ? E : never;

// 3. 递归扒多层 Promise 壳（内置 Awaited 原理）
type MyAwaited<T>    = T extends Promise<infer U> ? MyAwaited<U> : T;
```

1. **只能在 `extends` 右侧条件子句中登场**：`infer U` 不能脱离条件类型单独写，且推导出来的变量 `U` **只能在 `?` 后面的真分支（true branch）里使用**。
2. **支持 `infer U extends Constraint` 直接加约束**：TS 4.7 起支持在捕获的同时过滤类型，比如 `T extends [infer First extends string, ...any[]] ? First : never` 只捕获首元素为字符串的元组。
3. **多处同名 `infer` 的协逆变合并奇效**：如果同一个类型变量 `infer U` 同时出现在多个协变位置（如对象属性），TS 会推导出它们的**联合类型 `A | B`**；如果同时出现在多个逆变位置（如函数参数），TS 会推导出它们的**交叉类型 `A & B`**。

**考场口述**：

「`infer` 是配合条件类型使用的**待推导类型占位符**，专门用来从复合类型内部把局部类型『解构提取』出来。它只能写在条件类型的 `extends` 子句右侧，且推导出的类型变量只能在真分支里用。像内置的 `ReturnType`、`Parameters`、以及递归拆解 Promise 的 `Awaited`，底层全是用 `infer` 在对应结构槽位上捕获出来的。此外，当同名 `infer` 出现在多个函数参数这类逆变位置时，编译器会自动推导出它们的交叉类型。」

### 29.模板字面量类型

**记忆锚点**：**反引号跨界进类型，插槽遇联合自动展开笛卡尔积，配 `infer` 可拆路径参数**。

**痛点与直觉**：

前端有太多「有规律的字符串」：事件名 `onClick / onFocus`、CSS 方位 `margin-top / margin-bottom`、动态路由 `/user/:id/post/:postId`。以前这些全得退化成宽泛的 `string`，拼错了只能等线上报错。TS 4.1 把反引号模板字符串直接搬进了类型空间，让编译器学会了「**拼字符串**」和「**按格式拆字符串**」。

**核心机制**：

```
【1. 组合枚举（笛卡尔积自动展开）】
  type Dir = 'top' | 'bottom';   type Side = 'left' | 'right';
  type Corner = `${Dir}-${Side}`;  ──► 'top-left' | 'top-right' | 'bottom-left' | 'bottom-right'

【2. 模式匹配拆解路由参数（配合 infer）】
  type Param<P> = P extends `${string}:${infer K}/${infer Rest}` ? K | Param<`/${Rest}`>
                : P extends `${string}:${infer K}` ? K : never;
  Param<'/user/:uid/book/:bid'>  ──► 'uid' | 'bid'
```

1. **插槽遇联合自动算笛卡尔积**：模板插槽 `${U}` 里如果放入联合类型，TS 会把所有插槽的排列组合全部枚举出来（注意组合数超十万级会拖慢编译）。
2. **四大内置大小写转换器**：`Uppercase<S>`（全大写）、`Lowercase<S>`（全小写）、`Capitalize<S>`（首字母大写，写 `on${Capitalize<Event>}` 必备）、`Uncapitalize<S>`（首字母小写）。
3. **配合 `infer` 做编译期字符串解析**：在 `extends` 里写 `` `${infer Prefix}_${infer Suffix}` ``，编译器就能像正则分组一样把字符串按分隔符拆开，现代路由库（如 TanStack Router、Next.js 类型路由）全靠它自动提取路径参数。

**考场口述**：

「模板字面量类型把 JS 的反引号语法带进了类型系统，主要解决结构化字符串的类型校验问题。它有三大核心能力：第一是**笛卡尔积展开**，当插槽里传入联合类型时会自动枚举出所有拼接组合；第二是配合内置的 **`Capitalize` 等四个大小写工具类型**，把 `'click'` 自动映射成 `'onClick'`；第三是配合 **`infer` 做模式匹配**，比如在编译期直接从 `'/user/:id'` 这样的路由字符串里解析并提取出 `{ id: string }` 参数类型。」

## 工具类型

### 30.🌟常用工具类型有哪些

**记忆锚点**：**十二件工具分四屉：改修饰、裁键、筛联合、扒函数壳**——全是映射类型和条件类型拼出来的，不用背清单。

**痛点与直觉**：

业务里反复出现同一类变形：接口字段全改成可选、从大对象里抠出三个字段、从事件联合里剔掉内部事件、从回调函数里抽出返回值。每次手写映射类型既啰嗦又容易写错。内置工具类型就是类型层面的**标准扳手**：每个扳手只拧一种螺丝，看懂它的实现公式，遇到新变形就能自己造一把。

**核心机制**：

```
【四屉分类】
改修饰符   Partial / Required / Readonly     映射 + ? / -? / readonly
裁对象键   Pick / Omit / Record              映射挑键，或 Exclude 后再 Pick
筛联合项   Exclude / Extract / NonNullable   分布式条件类型，不要的分支变 never
扒函数壳   ReturnType / Parameters / Awaited infer 卡在返回位、参数位、Promise 里
```

1. **改修饰符是浅的**：`Partial<T>` 只给第一层加 `?`，`Readonly<T>` 只锁第一层；嵌套对象里的字段仍然必填、可写。要深度版本必须自己递归映射。
2. **裁键和筛联合是两套坐标系**：`Pick` / `Omit` 动的是对象的键；`Exclude` / `Extract` 动的是联合类型的成员。`NonNullable<T>` 就是 `Exclude<T, null | undefined>`，并不是对象工具。
3. **扒壳全靠 `infer`**：`ReturnType` 夹返回位，`Parameters` 夹参数元组，`Awaited` 递归夹 `Promise<infer U>`，直到剥到非 Promise 为止。

**考场口述**：

「常用工具类型我按四类记，不背名字清单。第一类改修饰符，`Partial`、`Required`、`Readonly`，本质是映射类型加减 `?` 和 `readonly`，而且都只作用于第一层。第二类裁对象键，`Pick` 挑键、`Omit` 去键、`Record` 用键联合生成对象。第三类筛联合成员，`Exclude`、`Extract`、`NonNullable`，靠分布式条件类型把不要的分支变成 `never`。第四类扒函数壳，`ReturnType`、`Parameters`、`Awaited`，全是条件类型加 `infer`。面试如果追问实现，我就把对应那一行公式写出来。」

### 31.🌟`Omit` 和 `Pick` 哪个更安全

**记忆锚点**：**`Pick` 写错键当场报错，`Omit` 写错键静默还你原类型**。

**痛点与直觉**：

重构时最怕的不是报错，是**没报错但语义已经错了**。`Omit<User, 'age'>` 里把 `'age'` 打成 `'aeg'`，类型检查一声不吭，你以为年龄字段删掉了，下游仍然能读到 `age`。这就像用修正带去盖一个不存在的字：纸面看起来「处理过了」，原文一个字没动。

**核心机制**：

```ts
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
type Pick<T, K extends keyof T>   = { [P in K]: T[P] };

// Omit<User, 'aeg'>
//   Exclude<keyof User, 'aeg'>  === keyof User     什么都没排除
//   Pick<User, keyof User>      === User           静默失败
// Pick<User, 'aeg'>             直接报错，因为 'aeg' 不是 keyof User
```

1. **约束宽窄决定安不安全**：`Pick` 的第二个参数收在 `keyof T` 里，键必须真的存在；`Omit` 的 `K` 只约束成 `keyof any`（`string | number | symbol`），任意字符串都能过。
2. **静默路径就两步**：错键进 `Exclude` 时一个成员都剔不掉，`keyof T` 原样回来，再 `Pick` 一次等于没操作。
3. **官方放宽是为了联合键，补救用 `StrictOmit`**：联合类型的 `keyof` 只剩公共键，若 `Omit` 也收成 `keyof T`，很多合法用法会写不出来。工程里要安全，自己收紧：`type StrictOmit<T, K extends keyof T> = Omit<T, K>`。

**考场口述**：

「删属性我会先说 `Omit`，但马上补一句：**`Pick` 比 `Omit` 安全**。因为 `Pick` 的键约束是 `keyof T`，拼错立刻报错；`Omit` 的键约束只是 `string | number | symbol`，拼错时 `Exclude` 什么都排除不掉，结果静默等于原类型。官方这么设计，是为了让 `Omit` 能处理联合类型上并不共有的键。业务代码里我习惯再包一层 `StrictOmit<T, K extends keyof T>`，把这个口子堵上。字节番茄二面问过怎么删掉接口的某个属性，答案就是 `Omit`，追问安全时把这条静默失败讲出来。」

**面经**：

- 字节 · 番茄二面：怎么删掉接口的某个属性。https://www.nowcoder.com/discuss/889546972099584000

### 32.`ReturnType` 和 `Parameters`

**记忆锚点**：**返回位夹 `infer R`，参数位夹 `infer P`；重载只认最后一条，泛型函数得到 `unknown`**。

**痛点与直觉**：

库函数的签名往往比你自己写的别名更准：重载、默认参数、this 类型都在里面。手抄一份 `type R = string` 会在库升级时悄悄过期。正确做法是把函数类型当成一只带壳的螃蟹，用 `infer` 从指定槽位把肉掏出来，签名一变，你的别名自动跟着变。

**核心机制**：

```ts
type MyReturnType<T>  = T extends (...args: any[]) => infer R ? R : never;
type MyParameters<T>  = T extends (...args: infer P) => any ? P : never;

function identity<T>(x: T): T { return x; }
type R = ReturnType<typeof identity>;   // unknown，T 还没实例化
```

1. **槽位决定抽什么**：`infer R` 放在 `=>` 右边抽返回值；`infer P` 放在参数列表抽元组。`ConstructorParameters`、`InstanceType` 是同一招换到 `new (...args) =>` 上。
2. **重载只取最后一条签名**：条件类型匹配重载时，编译器认的是实现签名（通常写在最后），前面的公开重载会被忽略。抽重载函数前要看最后那条是不是你想要的。
3. **泛型函数抽出来是 `unknown`**：`identity` 的 `T` 还没被调用方填上，编译器无法发明一个具体返回类型，于是退化成 `unknown`。要具体类型，先用具体参数实例化，再 `ReturnType`。

**考场口述**：

「`ReturnType` 和 `Parameters` 都是条件类型加 `infer`：一个夹在箭头右边抽返回值，一个夹在参数列表抽成元组。使用时有两个坑要主动说出来。第一，函数有重载时，它只匹配**最后一条签名**。第二，直接对未实例化的泛型函数取 `ReturnType`，得到的是 `unknown`，因为类型参数还没被填上。`Awaited` 是同一思路的递归版，一直 `infer` 到不再是 Promise 为止。」

### 33.`Record` 和索引签名

**记忆锚点**：**`Record` 能锁死具体键联合，索引签名是「任意这种键都算」的大门**。

**痛点与直觉**：

配置表经常要表达两种完全不同的形状：「必须有 `a` 和 `b` 两个键」和「随便什么字符串键都行」。写成同一种 `{ [k: string]: number }` 会把第一种的漏键检查也放掉。`Record` 的价值就是：键如果是有限联合，它就生成**有限个具名属性**；键如果是 `string`，它才退化成索引签名。

**核心机制**：

```ts
type Open = Record<string, number>;     // { [k: string]: number }
type Shut = Record<'a' | 'b', number>;  // { a: number; b: number }  漏键就报错
```

1. **键的宽度决定产物**：`K` 是 `string | number | symbol` 的宽类型时，`Record` 等价于索引签名；`K` 是字面量联合时，每个成员变成一个必填具名键。`K` 若不是这三种键的子类型，直接报错。
2. **索引签名读缺失键默认当值存在**：`dict[someString]` 的类型是 `V`，不是 `V | undefined`。这是历史行为，`noUncheckedIndexedAccess` 会把它改成 `V | undefined`，强迫你处理缺键。
3. **`Record` 是类型别名，不能声明合并**：要可扩展的字典形状用 `interface`；`Record` 适合「键集合已经定死」的映射表。

**考场口述**：

「`Record<K, V>` 和索引签名的差别在键。`Record<string, number>` 和 `{ [k: string]: number }` 等价，都是任意字符串键；但 `Record<'a' | 'b', number>` 会展开成两个具体必填属性，漏一个就报错，索引签名做不到这点。另外索引签名读一个不存在的键，类型上仍是 `V` 而不是 `V | undefined`，要堵住这个洞得开 `noUncheckedIndexedAccess`。`Record` 本身是类型别名，不能像 interface 那样声明合并。」

## 数据类型

### 34.数组和元组

**记忆锚点**：**数组是「同一型号、长度不限」的箱子；元组是「每个格子型号写死、格子数也写死」的托盘**。

**痛点与直觉**：

`useState` 返回的是值和更新函数，两者类型不同，还要按位置解构。如果只给一个 `any[]`，调用方完全不知道第 0 个是状态、第 1 个是 setter。元组把**位置**变成类型的一部分：第几个格子装什么，多一个少一个都不行。

**核心机制**：

```ts
const arr: number[] = [1, 2, 3];          // 同质，长度不进类型
const pair: [string, number] = ['a', 1];  // pair[2] 直接报错
const rest: [string, ...number[]] = ['a', 1, 2, 3];
const opt: [string, number?] = ['a'];
const locked = [1, 2] as const;           // readonly [1, 2]
```

1. **长度是类型**：定长元组访问越界下标会报错；数组的下标类型始终是元素类型（再叠加 `noUncheckedIndexedAccess` 才变可空）。
2. **三种变体够覆盖函数签名**：可选元素 `number?`、剩余元素 `...number[]`、只读元组 `readonly [1, 2]`。`Promise.all`、`Object.entries`、Hooks 的返回值都是这套。
3. **`as const` 把数组收成只读元组**：推断从 `number[]` 收窄成 `readonly [1, 2]`，字面量不再被拓宽。想要可变元组就不要加 `as const`。

**考场口述**：

「数组和元组的差别就一句：数组只约束元素类型，长度是运行时的事；元组把每个位置的类型和长度都写进类型。所以 `tuple[2]` 在越界时编译期就报错。工程里多返回值、`useState`、`Promise.all` 都靠它。变体有三个：问号表示该位置可缺，`...T[]` 表示后面还有一段同质元素，`as const` 会得到只读元组。可变参数函数的参数列表，本质就是一条剩余元组。」

### 35.`Map`、`Set` 和对象、数组

**记忆锚点**：**键要任意值用 `Map`，只想去重用 `Set`，字段名固定用对象，顺序扫描用数组**。

**痛点与直觉**：

对象看起来能当字典，但键会被收成字符串，数字键还会被提前排到前面，而且原型链上的 `toString` 可能被当成「有这个键」。需要一张干净的键值表时，对象是一张会串味的便签；`Map` 是按插入顺序上锁的档案柜，键可以是对象本身，不会跟原型链搅在一起。

**核心机制**：

```
对象    键只能 string|number|symbol    数字键顺序特殊    适合字段固定的结构
Map     键是任意值，按引用区分          严格插入序        频繁增删的字典
Set     成员按 SameValueZero 去重       插入序            去重、成员判断
数组    按下标                          有序              需要遍历和按下标取
```

1. **对象键和 `Map` 键不是一回事**：`Map` 用引用相等区分对象键，两个内容一样的对象是两把不同的钥匙。对象会把键转成字符串或 symbol。
2. **`WeakMap` / `WeakSet` 的键是弱引用**：键对象被回收后条目一起消失，因此不能遍历、没有 `size`。适合给外部对象挂私有缓存，避免缓存本身把对象钉死。
3. **`Set` 去重用 SameValueZero**：`NaN` 能被去掉重复的自己，`+0` 和 `-0` 算同一个。这和 `===` 不同，`===` 认为 `NaN` 不等于 `NaN`。

**考场口述**：

「选型我按键的需求说。字段名在写代码时就定死，用对象；键可能是对象、或者要严格保持插入顺序并频繁增删，用 `Map`；只要去重和 `has`，用 `Set`；要按下标顺序扫描，用数组。补充三个易混点：`Map` 的对象键按引用比，不是按内容比；`WeakMap` 是弱引用，键回收后条目消失，所以不能遍历；`Set` 用 SameValueZero，`NaN` 可以去重，这点和 `===` 相反。」

### 36.`readonly` 数组

**记忆锚点**：**只读数组是「可借不可改」的视图：普通数组能赋给它，它不能赋回普通数组**。

**痛点与直觉**：

数组是协变的。如果函数参数写成 `Animal[]`，调用方传进 `Dog[]`，函数内部一个 `push(new Cat())` 就把猫塞进了狗数组，类型系统完全看不出来。把参数收成 `readonly Animal[]` 等于摘掉所有变异方法，这条污染路径直接被焊死。

**核心机制**：

```
Dog[]  ──可赋给──►  readonly Animal[]     只读视图，push/pop/splice 全部消失
readonly Animal[]  ──不能赋给──►  Animal[]  否则调用方还能变异，只读承诺破产

readonly T[][]  只锁外层；内层数组仍然可变
```

1. **赋值方向是单向的**：可变数组可以当作只读数组用；只读数组不能交回给会 `push` 的参数，否则只读就没有意义。
2. **它修的是数组协变洞**：禁止 `push`、`pop`、`splice`、按下标赋值之后，函数就无法把更宽的元素写进更窄的数组。
3. **`readonly T[]` 与 `ReadonlyArray<T>` 等价，而且是浅的**：只读修饰不会递归进元素。元素本身若是数组或对象，里面仍可改。

**考场口述**：

「`readonly T[]` 会拿掉所有变异方法，是数组的只读视图，和 `ReadonlyArray<T>` 完全一样。赋值方向要记牢：普通数组可以赋给只读数组，只读数组不能赋回普通数组。这样做是为了堵住数组协变的洞——参数若写成可变的 `Animal[]`，函数里 `push` 一只猫就能污染调用方的 `Dog[]`。另外它是浅只读，`readonly T[][]` 只锁外层。」

### 37.`bigint` 和浮点数

**记忆锚点**：**`number` 是 64 位浮点，安全整数到 2^53-1；再大用 `bigint`，金额用整数分**。

**痛点与直觉**：

IEEE754 双精度用二进制科学计数法存小数。`0.1` 在二进制里是无限循环，加完 `0.2` 对不上 `0.3`。整数也一样：尾数只有 53 位，超过 `9007199254740991` 之后，相邻整数在 `number` 里会并成同一个值。订单号、雪花 ID 一旦走 `JSON.parse` 进 `number`，末几位就丢了，而且类型检查发现不了——它仍然是合法的 `number`。

**核心机制**：

```
number   安全整数区间  -(2^53-1) .. 2^53-1     0.1 + 0.2 !== 0.3
bigint   字面量带 n，精度随数字变长            不能和 number 直接运算
JSON     JSON.parse / JSON.stringify 不认识 bigint，大整数 ID 会先被截成 number
```

1. **金额不要用 `number`**：用「分」这种整数，或用十进制字符串。展示时再格式化，计算时不碰二进制小数。
2. **`bigint` 是另一套类型**：不能和 `number` 混算，不能丢进 `Math.*`，`JSON.stringify` 遇到它会抛错。和 `number` 互转必须显式 `Number()` / `BigInt()`，并且要先确认没超出安全范围。
3. **接口里的大整数 ID 用字符串**：`JSON.parse` 在进 JS 之前就把超长数字变成不精确的 `number`。后端直接发字符串，或换用保留大整数的解析器，类型上标 `string` 而不是 `number`。

**考场口述**：

「`number` 是双精度浮点，不是数学实数。小数上 `0.1 + 0.2` 不等于 `0.3`；整数上超过 `2^53 - 1` 就不再精确。所以金额用整数分或字符串，不用 `number`。更大的整数用 `bigint`，但它不能和 `number` 混算，`JSON.stringify` 也会抛错。线上最常见的事故是雪花 ID 走 `JSON.parse` 被收成 `number`，末位丢失，类型系统看不出来。解法是后端发字符串。」

## 错误处理

### 38.🌟TS 里怎么做错误处理

**记忆锚点**：**`throw` 能抛任何值，所以 `catch` 里是 `unknown`，先收窄再读 `message`**。

**痛点与直觉**：

Java 的受检异常会把「可能抛什么」写进签名，编译器逼调用方处理。JS 没有这条规矩：函数签名不声明异常，而且 `throw 'boom'`、`throw 404` 都合法。于是 `catch (e)` 若默认成 `any`，下一行 `e.message` 在抛字符串时直接运行时崩溃。TS 4.4 起把这个变量改成 `unknown`，等于把外来包裹锁进保险箱，不开箱不准拆。

**核心机制**：

```ts
try {
  await doSomething();
} catch (e) {                         // e: unknown
  if (e instanceof Error) {
    console.error(e.message, e.stack);
  } else {
    console.error('非 Error', e);
  }
}
```

1. **收窄优先用 `instanceof Error`，跨窗口不可靠**：iframe、worker 里的 `Error` 和主窗口不是同一个构造函数，`instanceof` 会失败。稳妥判断是 `typeof e === 'object' && e !== null && 'message' in e`。
2. **自定义错误要改写 `name`**：`class AppError extends Error` 之后若不赋 `this.name = 'AppError'`，`name` 仍是 `'Error'`，日志和 `errors.As` 一类的分支会对不上。ES2022 可以用 `new Error(msg, { cause })` 把原始错误串成链。
3. **类型系统不追踪抛出**：调用方从签名上看不到函数会抛什么。可预期的业务失败不要只靠 `throw`，放到下一节的返回值里；`throw` 留给真正的缺陷和不可恢复故障。

**考场口述**：

「TS 没有 Java 那种受检异常，函数签名不会声明自己抛什么，而且 JS 允许 `throw` 任意值。所以在 `useUnknownInCatchVariables` 打开后——这也是 `strict` 的一部分——`catch` 变量是 `unknown`，必须先收窄才能读 `message`。我一般用 `instanceof Error`；如果代码会跨 iframe，就改成检查 `'message' in e`，因为跨窗口 `instanceof` 会失效。自定义错误类要手动把 `name` 写成自己的类名，需要错误链时用 ES2022 的 `cause`。」

### 39.判别联合做错误返回

**记忆锚点**：**可预期的失败写成 `{ ok: true, data } | { ok: false, error }`，调用方不分支就拿不到数据**。

**痛点与直觉**：

`throw` 可以被悄悄忽略：不写 `try` 代码照样通过编译，错误等到线上才炸。把失败变成返回值的一种形态之后，数据被关在 `ok: true` 那个分支里，调用方不先看 `ok`，编译器就不让他碰 `data`。这和收窄是同一套机关，只是判别字段从类型标签换成了业务自己的 `ok`。

**核心机制**：

```ts
type Result<T, E = Error> =
  | { ok: true; data: T }
  | { ok: false; error: E };

function parse(s: string): Result<number> {
  const n = Number(s);
  return Number.isNaN(n)
    ? { ok: false, error: new Error('NaN') }
    : { ok: true, data: n };
}
// r.ok 为 true 时 r.data 是 number，否则只能读 r.error
```

1. **判别字段必须是字面量**：`ok: true` 和 `ok: false` 是两条互斥的臂。写成 `ok: boolean` 就失去收窄能力，两个分支会粘在一起。
2. **失败变成值，就能传递和变换**：可以 `map`、可以放进数组、可以在边界集中记录，不依赖调用栈展开。这是 Rust `Result`、Haskell `Either` 的同一思路。
3. **不要拿它替换所有 `throw`**：校验失败、余额不足、解析失败用 `Result`；断言失败、运行环境损坏仍用抛出。第三方库若只会抛，在边界上捕一次，翻译成 `Result` 再往里传。

**考场口述**：

「业务上可预期的失败，我更倾向返回判别联合，而不是 `throw`。类型写成 `{ ok: true; data: T } | { ok: false; error: E }`，调用方不判断 `ok` 就访问不到 `data`，编译器强制处理。这里的关键是 `ok` 必须是字面量类型，写成 `boolean` 就收窄不了。代价是每一层都要显式传递，和只抛异常的第三方库也不直接兼容，所以我会在边界把异常翻译成 `Result`。真正的程序缺陷仍然抛出去。」

## 装饰器

### 40.🌟装饰器是什么

**记忆锚点**：**声明处贴标签，编译后变成包一层的函数调用；Nest 仍锁在旧版，因为新版没有参数装饰器**。

**痛点与直觉**：

日志、鉴权、缓存如果写进每个方法体，业务代码会被横切逻辑淹没。Java 用切点表达式加动态代理在外部织入；TS 的做法是在方法头上贴一个 `@log`，编译器把它改写成「用函数把原方法包起来」。标签看起来像注释，产物里却是真实的运行时调用——它属于类型擦除的四个例外之一。

**核心机制**：

```
旧装饰器 experimentalDecorators     新装饰器 TS 5.0 起默认（TC39 Stage 3）
  支持参数装饰器                      没有参数装饰器
  可 emitDecoratorMetadata            不发 design:paramtypes
  NestJS / TypeORM / 旧 Angular       新写的装饰器

多个装饰器：求值自上而下，应用自下而上
方法装饰器先于类装饰器执行；参数装饰器最早
```

1. **它是编译期改写，不是运行时反射**：`@log` 变成一次包装函数调用，把原方法换掉。TS 语言本身没有 Java 式反射；`emitDecoratorMetadata` 只是按约定写出 `design:paramtypes`，再由 `reflect-metadata` 读走。
2. **NestJS 短期不会换新装饰器**：依赖注入要读构造函数参数的类型，而「参数装饰器」和「参数类型元数据」恰好是 Stage 3 装饰器不支持的两样。所以 Nest 项目必须开 `experimentalDecorators` 和 `emitDecoratorMetadata`。
3. **顺序用「先收集、后套娃」记**：求值从上到下，真正包上去从下到上，和函数组合 `f(g(x))` 一样，最靠近方法的那一层最里。

**考场口述**：

「装饰器是挂在类、方法、属性或参数上的包装钩子，编译后会留下真实的函数调用，不是被擦掉的类型。现在有两套：TS 5.0 起默认的是 TC39 Stage 3，不支持参数装饰器，也不发类型元数据；NestJS、TypeORM 仍要求 `experimentalDecorators` 加 `emitDecoratorMetadata`，因为它们的依赖注入靠构造函数参数类型，而这正是新装饰器缺的两样。多个装饰器的顺序是求值从上到下、应用从下到上。TS 本身没有 Java 那种反射，只是用元数据模拟。」

## 工程实践

### 41.`strict` 打开了哪些

**记忆锚点**：**`strict` 是一组开关的总闸；收益最大的两把是 `strictNullChecks` 和 `noImplicitAny`**。

**痛点与直觉**：

很多人以为 `strict: true` 是一个单独算法。它其实是配电箱里的总闸，合上之后一批独立开关一起接通。迁移老项目时如果一把全推上，报错会混成一团，分不清哪条规则在响。按「先禁隐式 any，再禁空值混入」的顺序推，每一批报错都有同一张脸。

**核心机制**：

```
strict
 ├─ strictNullChecks              null / undefined 不能赋给其他类型
 ├─ noImplicitAny                 推不出来就报错，不许默默变成 any
 ├─ strictFunctionTypes           函数参数按逆变检查
 ├─ strictPropertyInitialization  类属性必须在构造里就绪
 ├─ strictBindCallApply           bind / call / apply 也查参数
 ├─ alwaysStrict                  产物写上 "use strict"
 └─ useUnknownInCatchVariables    catch 变量是 unknown
```

1. **迁移先开 `noImplicitAny`**：它把「忘了标类型」集中暴露出来，改动点清晰。随后再开 `strictNullChecks`，改动最多，但堵的是线上 `Cannot read properties of undefined`。
2. **类属性用构造函数赋值，而不是 `!`**：`strictPropertyInitialization` 要求属性在构造结束前有值。非空断言 `!` 只是让检查闭嘴，构造函数里赋值或给默认值才是真的初始化。
3. **其余开关对得上前面的题**：`strictFunctionTypes` 就是参数逆变那一节的开关；`useUnknownInCatchVariables` 就是 `catch` 为 `unknown` 的开关；`strictBindCallApply` 让 `call` 的参数和函数签名对齐。

**考场口述**：

「`strict` 不是一条规则，是一组开关的合集。里面最重要的两个是 `noImplicitAny` 和 `strictNullChecks`：前者禁止推不出来就变成 `any`，后者禁止 `null` 和 `undefined` 混进其他类型。老项目我会先开前者，再开后者。其余我能对上号的有三个：`strictFunctionTypes` 打开函数参数的逆变检查，`useUnknownInCatchVariables` 让 `catch` 变成 `unknown`，`strictPropertyInitialization` 要求类属性在构造函数里初始化，不要靠非空断言蒙混。」

### 42.`d.ts` 文件

**记忆锚点**：**`.d.ts` 只留类型、不留实现；文件里一旦出现 import，它就从全局脚本变成模块**。

**痛点与直觉**：

TS 要给已经写成 JS 的库、以及 `.svg` 这种非代码文件配类型，但不能把实现再写一遍。`.d.ts` 就是一份**只有货物清单、没有货物的舱单**。舱单放错位置时，编译器会当作没看见：要么没被 `include` 扫到，要么因为文件里写了 `import`，这份声明变成了模块，里面的全局变量不再自动进入全局。

**核心机制**：

```ts
declare module '*.svg' {
  const src: string;
  export default src;
}

export {};
declare global {
  interface Window {
    __APP_CONFIG__: AppConfig;
  }
}
```

1. **三种正当用途**：给无类型的 JS 库补声明、扩展 `Window` 这类全局、给 `.svg` / `.css` 模块一个类型。业务实现不要写进 `.d.ts`。
2. **不生效先查三处**：文件不在 `include` 里；`typeRoots` 或 `types` 把它排除了；文件含有 `import` / `export`，已经是模块，顶层 `interface Window` 不会合并进全局，必须包进 `declare global`。
3. **`declare module` 和 `declare global` 方向相反**：前者给某个模块名（包括 `*.svg` 这种模式）提供类型；后者在模块文件内部打开一个口，把声明送回全局作用域。

**考场口述**：

「`.d.ts` 是只有类型声明、没有实现的文件，用来给 JS 库、全局变量和非代码资源补类型。最容易配错的一点是：文件里只要出现 `import` 或 `export`，它就变成模块，顶层声明不再自动是全局的，扩展 `Window` 必须写在 `declare global` 里。另外还要确认它落在 `include` 范围内，没有被 `types` 或 `typeRoots` 排除。`declare module '*.svg'` 是在给一类模块名补类型，和 `declare global` 不是一回事。」

### 43.`import type`

**记忆锚点**：**`import type` 是一张「编译后整行消失」的收据；打包器只看语法，不猜这个导入是不是类型**。

**痛点与直觉**：

类型会被擦除，纯类型导入按理不该留在产物里。但 esbuild、Vite 这类工具是**单文件转译**，它不跑完整的类型检查，看到 `import { User } from './types'` 时无法判断 `User` 是类型还是值。于是它可能把这行原样留下，运行时去加载一个只导出类型的模块，直接报模块不存在，或者把类型导入变成真实的循环依赖。

**核心机制**：

```ts
import type { User } from './types';                 // 产物中整行删除
import { createUser } from './api';                  // 保留
import { type User, createUser } from './both';      // 只删 User 这个绑定

// verbatimModuleSyntax: true 之后，类型导入必须写 type，值导入必须是值
```

1. **`import type` 与行内 `type` 都是语法标记**：前者整行只引进类型；后者在同一行里混用时，标出哪些绑定是类型。转译器不需要类型检查器就能决定删哪一段。
2. **`isolatedModules` / `verbatimModuleSyntax` 逼你写明**：逐文件转译无法跨文件判断导入性质。`verbatimModuleSyntax` 打开后，该标 `type` 而不标，直接报错，避免产物里留下运行时导入。
3. **漏标的后果在运行时，不在类型检查**：`tsc --noEmit` 可能全绿，页面一跑才发现循环依赖或模块解析失败。这和「类型检查拦不住打包」是同一条边界。

**考场口述**：

「`import type` 用来标明这次导入只取类型，编译后整行会被删掉。之所以要显式写，是因为 Vite 和 esbuild 做单文件转译，看不到完整类型信息，无法判断一个导入是类型还是值，有可能把纯类型导入留到运行时。行内可以写 `import { type User, createUser }`，只擦掉类型绑定。打开 `verbatimModuleSyntax` 之后，类型导入必须带 `type`，这样打包器和类型检查器看到的是同一份语法。」

### 44.类型测试

**记忆锚点**：**`@ts-expect-error` 是「这里必须报错」；`@ts-ignore` 是「别出声」。工具类型要用类型断言测试兜住静默失败**。

**痛点与直觉**：

第 31 节的 `Omit` 写错键时，测试代码照样编译通过，因为结果只是「悄悄等于原类型」。普通单测断言的是运行时的值，类型在编译后已经没了，单测看不见。类型测试断言的是**编译器的态度**：这个位置必须等于某个类型，或者这一行必须报错。

**核心机制**：

```ts
import { expectTypeOf } from 'expect-type';

expectTypeOf<ReturnType<typeof fn>>().toEqualTypeOf<string>();

// @ts-expect-error 字符串不能赋给 number；若这行不再报错，指令自己失败
const bad: number = 'a';
```

1. **`@ts-expect-error` 会在「居然没报错」时失败**：它要求下一行真的有类型错误。错误被重构修掉之后，这条指令变成多余，编译失败，提醒你删掉它。
2. **`@ts-ignore` 永远闭嘴**：下一行无论还有没有错都通过，不能当测试用。它只适合暂时压住来自第三方的、你改不了的报错。
3. **工具类型要断言「等于」，不要只断言「能赋给」**：`extends` 只能证明兼容，证明不了没有多出来的字段。`expect-type` 的 `toEqualTypeOf` 比双向 `extends` 更适合锁死 `Pick`、`Omit`、`ReturnType` 的结果。

**考场口述**：

「类型在编译后会被擦除，所以普通单测看不住工具类型。我会用 `expect-type` 这类库断言两个类型完全相等，防止 `Omit` 写错键时静默变回原类型。注释指令里，`@ts-expect-error` 表示下一行必须报错，一旦不再报错，这条指令自己会失败；`@ts-ignore` 是永远忽略，不能拿来做测试。断言时要断言相等，不要只写 `extends`，否则多出来的字段发现不了。」
